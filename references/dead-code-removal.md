# 死代码判定与删除（Dead Code Removal）

> 死代码不是「删掉更干净」的优化项，而是一次**存在性变更**。
> 删错一个低频路径（年末结算、对账、admin 恢复路径）的代价，
> 远高于留着一段冗余代码。
>
> **本协议的核心是"取证"，不是"搜索"。**

---

## §D.0 诊断：先确认走哪条路线

死代码判定完全取决于**你能拿到什么证据**。第一步永远是问这一个问题：

```
这个项目有线上流量与可观测手段吗？
（服务端日志能否查？APM / 网关访问日志 / DB 审计日志有没有？）
```

| 情况 | 路线 | 判定依据 | 证据强度 |
|---|---|---|---|
| 有线上日志/APM/网关日志/DB 审计 | **路线 A：运行时取证** | 真实触发记录 | 强 |
| 无线上可观测手段 | **路线 B：纯本地入口可达性** | 入口是否存在且能触达该符号 | 弱（见 §D.0.1） |

**不要把两条路线的结论混在一起报告。** 路线 B 的结论必须显式标注证据等级，
否则后续接手的人会误以为它和路线 A 一样可靠。

### §D.0.1 路线 B 的本质不对称（必须理解）

纯本地取证有一个无法回避的性质：

> **找到触发路径 → 能确定它是活的（结论可靠）。
> 找不到触发路径 → 只能说它是"候选死代码"，不能说它是死的（结论不可靠）。**

原因：本地取证只能覆盖**你想到去点的路径**。它天然看不见：

| 天然盲区 | 后果 |
|---|---|
| 低频路径（年末结算、月度对账、季度报告） | 被误判为死代码 |
| 运营/管理侧隐藏入口（后台页、运维脚本、DB 直连） | 被误判为死代码 |
| 开关后的路径（feature flag 默认关、灰度未开） | 被误判为死代码 |
| 异常/恢复路径（补偿、重试、对账修复） | 被误判为死代码 |
| 未上线功能（尚未接入口、计划中的功能） | 被误判为死代码 |
| 纯测试引用（测试直接调它） | 误删会导致测试红 |

因此路线 B 下**必须收窄删除范围**，并强制走 §D.5 的保守处置。
把这条写进报告，不要假装两条路线等价。

## §D.1 候选提取（只找嫌疑人，不定罪）

无论哪条路线，第一步都是产出**候选清单**，此时不做任何结论。

```
# 语言无关的近似手段
# 1) 未被引用的导出符号 / 未被调用的私有函数（优先用编译器或 linter）
#    tsc --noUnusedLocals / ruff F401,F811 / go vet / cargo clippy / IDE 的 unused 检查
# 2) 开关与开关后的路径
grep -rn "flag\|toggle\|isEnabled\|enable\|rollout\|canary"
# 3) 显式废弃标记
grep -rn "TODO\|FIXME\|DEPRECATED\|@deprecated\|obsolete\|unused\|unreachable"
# 4) 注释掉的代码块
grep -rn "^\s*//\|^\s*#\|^\s*\*"
# 5) 遗留命名
grep -rn "v1\|legacy\|old\|backup\|_bak\|copy\|_2\b"
# 6) 历史痕迹
git log --diff-filter=D --name-only
```

候选写入 `DEAD-CODE-CANDIDATES.md`
（模板见 [templates/DEAD-CODE-CANDIDATES-template.md](../templates/DEAD-CODE-CANDIDATES-template.md)），
每条只记录：位置、类型猜测、发现方式。**不写结论。**

> [!WARNING]
> **`grep` 零命中不是删除依据。** 以下都能让静态搜索完全失效：
> 反射与动态派发（`getattr`、`Class.forName`、DI 容器按名注入）、
> 字符串引用（配置里的类名、数据库里存的 handler 名）、
> 外部触发（客户端旧版本、cron、webhook、消息订阅、DB 触发器、BI 直连查表）、
> 序列化（旧持久化数据按字段名找类）、构建期（注解处理器、宏、代码生成）、
> 测试引用。
> **搜索只能用来找候选，不能用来定死。**

## §D.2 路线 A：运行时取证

### A1 证据分级

| 强度 | 证据 | 取证方式 | 能否定论 |
|---|---|---|---|
| **A** | **运行时触发记录** | 服务端日志、APM、网关访问日志、DB 审计/慢查询日志 | ✅ **唯一能单独定论** |
| **B** | 入口可达性 | 路由注册表、定时任务清单、消息订阅、CLI 命令表、对外导出清单 | ✅ 能 |
| **C** | 调用链可达 | 从 A/B 类入口静态回溯 | ⚠️ 有动态派发盲区，仅作辅助 |
| **D** | 测试覆盖 | 测试实际触达 | ⚠️ 不算生产活性，但删了会红 |
| **—** | 搜索无结果 | grep 零命中 | ❌ **不构成证据** |

**判定规则**：

- 拿到 A 或 B → **活着**，立即出队。
- 只有 C 或 D → 降级为「待定」，走 §D.4 分类处置。
- 全无 → 候选死代码，进入分类。

### A2 金标准：给候选打点，跑满完整周期

这是路线 A 下最可靠的做法，**优于任何静态推断**。

```python
# 在候选函数入口加一次性计数（示意，语言无关）
logger.warn("DEADCODE_PROBE: <symbol> reached")
# 或 counter.inc("probe.<symbol>")
```

- **观察窗口必须覆盖完整业务周期**：日、周、月结、季度、年度、大促、对账窗口。
  一个「没人调用」的对账函数可能一年只跑一次。
- 线上不便打点时：用低频采样日志或指标计数，**不要用全量日志**。
- 打点代码本身必须可一键移除，且不要引入新的行为分支。

### A3 探测结果记录

每个候选记录：探测符号、打点方式、观察起止时间、命中次数、覆盖的业务周期。
**零命中 + 覆盖完整周期**才算通过。只观察了 3 天就说「没人用」是不合格的。

## §D.3 路线 B：纯本地入口可达性

无线上日志时，唯一的证据来源是**入口 + 调用链**。核心动作是：**先建入口清单，
再判断能否从入口走到目标符号。**

### B1 硬规则：没建完入口清单，不许判死代码

先回答：**这个系统对外暴露的入口有哪些？**

| 入口类型 | 查找位置 |
|---|---|
| HTTP 路由 | 路由注册处、网关配置、框架的路由表 |
| 页面 / UI 交互 | 前端路由、菜单、页面组件、按钮绑定 |
| 定时任务 | cron 配置、调度器注册、任务清单 |
| 消息订阅 | 队列/topic 消费者注册 |
| CLI / 脚本 | 命令行入口、运维脚本、部署脚本 |
| DB 触发器 / 存储过程 | 迁移文件、schema |
| 对外导出 | 库的 public API、SDK 导出清单 |
| 第三方回调 | webhook 处理器注册 |

**完整性自检**：凡是**用户能感知到的功能**，必须能对应到一个入口。
对应不上的，说明入口清单没建全 —— **回去补，不要继续判定**。
这是最容易出错的一步。

### B2 有 UI 时：以 UI 可达性为准

**规则**：UI 中能触达并调用了该功能 → **非死代码**；UI 中找不到触达路径 → 候选死代码。

但「UI 可达」不等于「页面上有这个名字」，必须**建立完整链路**：

```
页面/路由  →  组件或动作（按钮、菜单、表单提交）
          →  API 调用（前端实际发出的请求）
          →  后端路由注册处（确认该路由真的被注册）
          →  handler / controller
          →  目标符号
```

**判定表**：

| 观察 | 判定 | 处置 |
|---|---|---|
| 完整链路走通，后端路由确实注册 | **活着** | 出队，记录链路证据 |
| 链路走通但被开关/权限拦截 | **活着（受限）** | 走 §D.4 T2：先关开关观察，再决定 |
| 后端路由未注册 / 无前端调用 | 候选死代码 | 进入分类 |
| 前端有调用但后端无对应路由 | **疑似幽灵契约** | 单独标记，这不是死代码而是缺陷 |
| 页面存在但入口无任何链接指向（孤儿页） | 候选死代码（低置信） | 需人工确认是否靠 URL 直访使用 |

> [!CAUTION]
> **只检查前端路由表就下结论是错的。** 前端路由存在不等于有人访问，
> 更不等于后端逻辑被调用。必须走到**后端路由注册处**并确认调用链上的符号。
>
> 同理，「孤儿页」（无入口链接、只能靠 URL 直访）在纯本地模式下**无法判定**——
> 它可能只被运维或报表系统按 URL 调用。这类一律降级处置，不要直接删。

### B3 无 UI 时：看网关与注册点

按下列顺序取证：

1. **网关 / 反向代理配置** —— 有路由规则指向的路径即为活入口。
2. **路由注册表 / 控制器注解** —— 框架扫描到的路由即为活入口。
3. **调度与订阅注册** —— cron、定时器、消费者注册即为活入口。
4. **CLI 与脚本清单** —— 命令行入口、运维脚本、部署脚本即为活入口。
5. **对外导出清单** —— 被导出的公共符号即为活入口（被下游依赖）。
6. **本地日志文件** —— 即使是纯本地部署，通常也有日志落盘。
   检查历史日志里该符号是否出现过，这是路线 B 下**最接近 A 级的证据**。

> 第 6 条常被忽略。本地跑过的日志、测试输出、DB 的 query log、
> 甚至开发机的终端历史，都可以作为弱证据使用。

### B4 路线 B 的结论标注

路线 B 产出的每条「死代码」结论必须带上：

```
证据等级：B（入口可达性）
已覆盖入口：[路由 / UI / cron / 订阅 / CLI / 导出]
未覆盖入口：[列出无法检查的]
观察周期：不适用（无运行时数据）
置信度：高 / 中 / 低
```

**置信度为「低」的项，禁止直接删除**，只能标记待定或交用户裁决。

## §D.4 分类：不同类型，删除条件完全不同

| 类型 | 定义 | 删除前置条件 | 风险 | 路线 B 下 |
|---|---|---|---|---|
| **T1 不可达** | 无任何入口可达、无调用链、无运行记录 | 探测期零命中 + 引用全清 + 入口清单已建全 | 低 | 可删（置信度高时） |
| **T2 受限/可触发但不活** | 有入口，但被开关/权限/环境条件挡住 | **先把开关关掉观察一个周期**，再删；保留默认值变更记录 | 中 | **只关开关，不删代码** |
| **T3 数据死** | 代码可达，但历史数据已空或只服务旧表/列 | 现有数据一致性核查 + 合规保留期确认 + **删代码与删列分两批** | 中高 | 仅删代码，**保留表**并写文档 |
| **T4 重复实现** | 同一语义多份实现，只有一份在用 | 先做阶段 1 语义审计判定哪份对应真语义，再确认另一份零触达 | 中 | 先审计，不确定则不删 |
| **T5 注释掉的代码块** | 被注释的整段实现 | 直接删；commit message 记录「它曾是什么」 | 极低 | 直接删 |
| **T6 半成品抽象 / 伪抽象层** | 接口仅一个实现且无第二个的迹象、预留钩子 | 确认无计划依赖（问用户），再删 | 低 | 需问 roadmap |

### 各类的关键提醒

**T2 最值得强调。** feature flag 死代码的正确顺序是
**关开关 → 观察一个完整周期 → 再删代码**，而不是直接删。
关开关这个动作本身可逆，是零成本的信息收集。路线 B 下**到此为止**，不要继续删代码。

**T3 是唯一可能需要保留数据的情况。** 合规/审计可能要求保留历史数据若干年。
此时删代码但保留表，并**把「为什么留着一堆没人读的表」写进文档**——
否则下一个 agent 又会把它当幽灵概念删掉。

**T4 必须在语义审计之后做。** 哪一份实现对应真语义，属于阶段 1 的判断，
不是死代码判定的范畴。顺序颠倒会删错那一份。

**T6 需要问用户 roadmap。** 半成品抽象可能是「下个季度要接第二个实现」的预留。
代码里没有证据能回答这个问题。

## §D.5 删除执行协议

### 批次结构

```
批次 D<n>
├─ 删除前：git tag deadcode-<n>-before        ← 回滚锚点
├─ 静态检查：linter / unused-code 全过
├─ 行为基线全绿
├─ 删除（单一 T 类型、≤10 个文件）
├─ 删除后再跑基线；比对日志与指标无新异常
└─ 观察期（路线 A：≥1 个完整业务周期；路线 B：见下）→ 收尾
```

### 硬纪律

1. **删除必须单独成批。** 不与「命名归一」或「结构改动」混合。
   删除改变的是**代码的存在性**，混批后基线红了无法归因。
2. **`git revert` 是回滚机制**，不是「先注释掉留个备份」。
   删除就该真删。`// removed old impl, see git history` 这类注释
   是在制造新的 T5 死代码。
3. **commit message 必须记录删除理由与证据**：
   - 路线 A：`DEADCODE: <symbol> — 探测 32 天零命中，覆盖月末结算窗口`
   - 路线 B：`DEADCODE: <symbol> — 入口清单（路由/cron/订阅/CLI）与 UI 链路均无触达，证据等级 B，置信度高`
   - **禁止**写「看起来没用」「应该没人调」。
4. **路线 B 下强制收窄范围**：
   - 只删 T1（且置信度高）、T5、T6。
   - **T2 只关开关不删代码。**
   - **T3 只删代码保留数据，并写文档。**
   - **T4 先审计。**
5. **观察期不可省。** 路线 A 至少一个完整业务周期。
   路线 B 无运行时数据，改为：删除后由用户/团队**实际使用系统走一遍主要流程**，
   确认无异常；并在 `REARCH-STATE.md` 中登记观察项，留待下一轮验证。
6. **报告里必须写明证据强度。** 路线 B 的结论标注为低强度证据，
   并列出未覆盖的入口 —— 这是用户未来追责时唯一的依据。

### 删除后的验证

| 检查 | 路线 A | 路线 B |
|---|---|---|
| 行为基线全绿 | ✅ | ✅ |
| 静态/类型检查通过 | ✅ | ✅ |
| 入口链接无 404 / 无未定义符号 | ✅ | ✅ |
| 日志与指标无新异常 | ✅ 观察期 | ⚠️ 仅能看本地日志 |
| 主要业务流程走查 | ✅ | ✅ **必须** |
| 覆盖完整业务周期 | ✅ 必须 | ❌ 无法做到，登记观察项 |

## §D.6 完成标准

一批死代码删除算完成，当且仅当：

1. 每个候选都已完成判定并分类（T1–T6），**无静默丢弃**。
2. 每条删除结论都有证据记录，且标注了路线与证据等级。
3. 路线 B 的结论已列出未覆盖入口与置信度。
4. 删除批次单一类型、≤10 文件、独立提交、commit message 含证据。
5. 基线全绿、静态检查通过、主要流程走查通过。
6. `DEAD-CODE-CANDIDATES.md` 状态已更新；`REARCH-STATE.md` 已登记观察项。
7. 若存在保留数据（T3），保留原因已写入文档。

## §D.7 反模式清单

- ❌ 用 `grep` 零命中作为删除依据
- ❌ 只看前端路由表就判定功能可达/不可达
- ❌ 把「本地没点出来」当成「线上没人用」
- ❌ 直接删 feature flag 后面的代码（应先关开关观察）
- ❌ 删掉唯一一份正确实现（T3 未先做语义审计）
- ❌ 删除与命名改动混在同一批次
- ❌ 用注释掉的方式「保留备份」
- ❌ commit message 写「看起来没用」
- ❌ 路线 B 的结论不加证据等级标注，让后人以为它和运行时证据一样可靠
- ❌ 删完不登记观察项，下一轮又把它当新发现重新审计一遍
