# 安全协议（Safety Protocols）

在触碰任何涉及公共 API、共享状态、并发代码或没有测试覆盖的文件的重构之前，请完整阅读本文件。

---

## 首要原则（The Prime Directive）

> **每一次重构都让可观察行为保持完全一致。**

如果一项提议的改动改变了程序对外表现的东西——输出、副作用、抛出的错误、时序或公共契约——那它就**不是重构**。它是功能变更。功能变更在继续之前需要用户明确批准。

有疑问时，就问。一个 10 秒钟问题的代价低于一个生产系统崩溃的代价。

---

## §1 前置条件

**在做任何编辑之前，以下所有条件都必须为真：**

- [ ] 存在可运行的测试套件，或者用户已明确表示"没有测试——我接受这个风险"
- [ ] 在任何改动之前测试当前是通过的（如果刚确认过就不必再跑）
- [ ] 已理解改动范围——涉及哪些文件、哪些调用点、哪些调用方
- [ ] 范围内不包含数据库迁移、序列化格式变更或通信协议变更
- [ ] 你已经（不是略读地）读过每一个打算修改的文件

如果有任何前置条件不满足，停下来先解决它再继续。

---

## §2 编辑前检查清单（每一次编辑前都重复一遍）

- [ ] 我已读过该文件的当前状态（不是依赖会话早期的一次读取）
- [ ] 我知道自己要修改的函数/类的每一个调用点（已用 Grep 确认）
- [ ] 本次编辑恰好是一处逻辑操作——没有任何夹带
- [ ] 本次编辑之后测试可立即运行——没有任何编辑会让代码停留在损坏的中间状态
- [ ] 我能用一句话描述这次编辑改了什么、以及为什么行为得以保持

---

## §3 红线 —— 停下来先询问

**以下情形在做任何改动之前都需要用户明确确认：**

### 公共 API 变更
对以下任何一项的改动：
- 被导出或属于公共接口的函数/方法签名
- 被导出的符号名（类、函数、常量、类型）
- 模块的公共导入路径或导出结构

*为什么：* 当前代码库之外的调用方可能依赖它们。在这里你无法靠 grep 找到安全边界。

### 序列化格式变更
会改变以下任何一项的改动：
- JSON 键名或结构
- Protocol buffer 字段名或字段编号
- 数据库列名、表名或 schema
- 文件格式输出（CSV 表头、XML 标签名）
- 外部系统读取的环境变量名

*为什么：* 序列化后的数据会持久存在。旧数据、外部系统和配置文件可能静默损坏。

### 并发行为
会影响以下任何一项的改动：
- 锁的获取顺序
- Goroutine/线程/异步边界
- 副作用相对于 await 发生的位置
- 共享可变状态的访问模式

*为什么：* 并发 bug 是非确定性的，可能通过全部测试却造成生产事故。

### 错误契约变更
会改变以下任何一项的改动：
- 抛出或返回的错误类型
- 错误消息字符串（如果调用方会匹配它们）
- 某函数是否会在以前不会失败的地方失败（或反之）

*为什么：* 调用方中的错误处理往往没有测试，而且很脆弱。

### 无测试覆盖
在目标代码路径零测试覆盖的文件上继续操作。

*为什么：* 没有自动化手段验证行为是否得以保持。明确说明这一点，并要求用户确认。

### 近期并发编辑
目标文件在过去 24 小时内被另一位贡献者修改过（检查：`git log -1 --format="%ar" <file>`）。

*为什么：* 你对代码的理解可能已经过时。存在合并冲突或语义冲突的风险。

### 影响范围未知
对超过 1000 行的文件执行任何操作，而你还没有梳理出目标符号的所有调用方。

*为什么：* 你要改的东西可能有 50 个调用点，其中 48 个你从没见过。

### 智能体幻觉（Agentic Hallucinations）
在文件路径、符号名或测试失败错误是猜测或假定、而非通过主动执行工具（例如 `grep_search`、`list_dir`、`view_file` 或运行终端命令）验证过的情况下继续操作。

*为什么：* AI 智能体容易幻觉出不存在的文件，或者在没运行测试的情况下假定测试结果。始终通过工具输出直接验证路径是否存在、结果是否如此。

---

## §4 黄线 —— 警告并获得同意后继续

明确说明风险，等待用户确认后再继续：

| 情形 | 应给出的警告 |
|---|---|
| 重命名一个调用点超过 20 个的符号 | "这次重命名涉及 M 个文件中的 N 个调用点。我会全部更新。确认吗？" |
| 拆分一个被 5 个以上模块使用的类 | "这次拆分需要更新 N 处 import。请在我动手前确认新类名。" |
| 改变一个调用方超过 10 个的函数的参数顺序 | "正在改变一个被调用 N 次的函数的参数顺序。我会更新所有调用点。我找不到的调用方（例如动态调用、外部包）会静默损坏。" |
| 内联一个在多个文件中使用的函数 | "内联会删除这个函数。不在当前 grep 范围内的调用方都会损坏。确认吗？" |
| 重构测试代码 | "我正在修改测试代码。以前能捕获 bug 的测试现在可能因为错误的原因而通过。之后请仔细评审。" |

---

## §5 回滚协议

**当一次编辑之后测试失败时：**

1. **立即停止。** 不要尝试继续编辑。
2. **回退该编辑**——用 Edit 恢复之前的精确内容。
3. **明确说明回退：**
   > "正在回退：[操作名] —— [测试名] 失败，错误为：`[确切错误消息]`"
4. **先诊断**，再提出修复方案：
   - 是操作本身错了，还是拆解粒度太粗？
   - 是否存在预先阅读时看不见的隐藏依赖？
   - 这个操作最终是否改变了可观察行为？
5. **提出更安全的拆解方式。** 通常解决办法是把该步骤拆成两个更小的步骤，或者先修好某个前置条件。
6. **不要"向前修"**——不要为了让测试通过而改测试，也不要改其他代码来掩盖失败。要弄清楚重构为什么弄坏了测试。

**编辑前的状态留存：**
在任何编辑会话开始之前，记录当前状态：
```
git status         # 确认工作区干净，或知道已经改了什么
git stash list     # 确认没有意外的暂存改动
```

## §6 大型代码库协议

针对超过 500 行的文件，或涉及 3 个以上文件的改动：

**读取策略：**
- 不要读整个文件——先用 Grep 定位目标函数/类
- 只读目标及其直接上下文（周围 20–30 行）
- 如果需要理解整个类，只读字段声明和方法签名，再按需读取方法体

**调用方梳理 —— 任何重命名之前都必须完成：**
```
# 重命名任何符号之前，运行：
grep -rn "symbolName" .
# 统计：涉及多少个文件、多少个调用点？
# 如果调用点超过 20 个：黄线——继续前先警告用户
```

**改动顺序：**
按依赖顺序应用改动：
1. 先改最深的依赖（被提炼出来的那个函数）
2. 接着更新它的调用方
3. 最后更新 import 方

绝不要在"被调用方"以其新形态存在之前改动调用方。

**上下文容量纪律：**
工作记忆中同时最多保持 3 个文件。完成对一个文件的所有编辑后再打开下一个。重新读取超过 10 分钟未碰过的文件——它们可能已被早先的步骤改动。

## §7 信心等级

每次操作之前，评估你的信心：

| 等级 | 含义 | 行动 |
|---|---|---|
| **High（高）** | 从代码即可明显看出行为得以保持，并且测试已确认 | 继续 |
| **Medium（中）** | 行为保持看起来正确，但存在未测试的路径 | 说明假设，继续，并标记需要补充测试评审 |
| **Low（低）** | 不确定行为是否得以保持 | 停止。要么提升信心（更多阅读、更多测试覆盖），要么询问用户 |

绝不在 Low 信心下继续。一次你自己都不确定的重构，比不重构更糟。

## §8 架构重构协议

在对 `smells.md` 中**家族 6：架构违规**的任何坏味道采取行动之前，完整阅读本节。

架构重构是本技能中风险最高的类别，因为：
- 总会涉及多个文件
- 逻辑在层之间移动——即使代码看起来完全一样，也可能出现微妙的行为差异
- 跨层测试覆盖往往很薄，意味着失败可能不会立刻暴露
- 一次错误的爆炸半径很大：一个放错位置的职责可能级联成整个代码库的构建失败或运行时错误

---

### §8.1 前置条件（在触碰任何一个文件之前，全部必须为真）

- [ ] **当前架构已绘制。** 你知道哪个文件属于哪一层。用 Grep 追踪 import，识别真实的层结构——不要只凭目录名假设。
- [ ] **目标模式已获用户确认。** 绝不要假定用户想要 MVVM 而不是 MVP，或想要 Clean Architecture 而不是 Layered。明确询问：*"我应该朝哪种目标架构模式重构？"*
- [ ] **范围有界。** 你确切知道哪些文件会被改动、哪些不会。
- [ ] **被移动的逻辑有测试。** 如果没有测试覆盖被迁移的代码路径，停下来。要么先写测试（经用户批准），要么要求用户明确确认承担该风险。
- [ ] **被移动代码的所有调用点都已梳理。** 移动任何东西之前先运行 Grep。

---

### §8.2 移动不变式（The Moving Invariant）

**绝不在同一步中既改逻辑又改位置。**

每一次架构移动都使用这个三步序列：

```
Step A — Introduce:  创建新位置。旧位置委托给新位置。测试必须通过。
Step B — Redirect:   所有调用方改用新位置。旧位置现在是死代码。测试必须通过。
Step C — Remove:     删除旧位置。测试必须通过。
```

如果任何一步测试失败，只回退那一步——不要继续。不要向前修。

这条不变式适用于任何粒度：移动单个方法、整个类，或一组类，都遵循同一序列。

---

### §8.3 架构红线 —— 停下来先询问

以下情形在做任何改动之前都需要用户明确确认：

**移动带有副作用的代码（邮件、支付、任务队列、审计日志）**
副作用在目标架构中必须有清晰的归属者。把它们移到另一层会改变由谁负责、以及何时触发。问：*"这次移动之后，由哪一层负责触发[副作用]？"*

**在原本没有层的地方引入新层**
给一个缺少领域层的代码库添加领域层、用例层或仓储层是一项大型结构变更。梳理完整的爆炸半径（有多少文件需要 import 新层？）并取得用户确认后再继续。

**移动参与事务边界的代码**
如果被移动的代码当前位于一个数据库事务之内，把它移到另一层可能会让它落到事务范围之外。这可能导致部分写入或更新丢失。停下来，先确认事务归属再继续。

**移动属于序列化契约的类型**
如果被移动的类型（例如某个 ORM 实体）会被序列化为 JSON、写入数据库或通过协议共享，那么把它移到新层或重命名它可能破坏既有数据或外部消费方。这是 §3 中的一条红线——按红线来对待。

---

### §8.4 架构黄线 —— 警告并获得同意后继续

| 情形 | 应给出的警告 |
|---|---|
| 文件在超过 3 条 import 语句中跨越层边界 | "这个文件有 N 处跨层 import。我会逐一处理。请确认顺序。" |
| 为一个在 5 个以上文件中被查询的实体引入 Repository | "该仓储将影响 N 个文件。我会逐个迁移调用方。确认吗？" |
| 领域对象首次获得对外部事物的依赖 | "这是该领域对象的第一个外部依赖。请确认它属于领域层而非应用层。" |
| 添加一个跨越 2 个以上聚合根的 Use Case | "这个 Use Case 涉及多个聚合。这属于协调层面的关注点——请确认它属于应用层，而不是领域层。" |

---

### §8.5 架构绘制协议

在任何架构重构之前，产出一份分层图。在继续之前把它呈现给用户。

```
架构图 —— [项目名]：
┌─────────────────────────────────────────────┐
│ 表现层        │ controllers/, views/        │
│ 应用层        │ services/, use_cases/       │
│ 领域层        │ models/, domain/            │
│ 基础设施层    │ repositories/, db/, clients/│
└─────────────────────────────────────────────┘

发现的违规：
- controllers/OrderController.ts 从 repositories/ import（跳过了领域层）
- models/User.ts 从 services/ import（依赖方向反转）

目标模式：[由用户确认]
```

在这份图被呈现并确认之前，不要开始任何操作的 Step A。

---

### §8.6 架构重构的信心标准

架构变更在每一步之前都要求 **High（高）** 信心（见 §7）。Medium 信心并不充分，因为爆炸半径太大。

如果你不确定移动一段逻辑能否精确保持行为：
1. 再次读取源上下文和目标上下文
2. 追踪两个层中的所有调用方
3. 如果仍不确定，就不要移动——请用户先加一个把行为固定下来的测试

## §9 语义红线与契约迁移

在对 `smells.md` 中**家族 7：语义漂移**的任何坏味道采取行动之前，完整阅读本节。

语义级重构（改名、概念归一、概念的引入与删除）与架构重划是**两个不同的风险类别**：

- 架构重划的风险在**位置**——逻辑搬来搬去，爆炸半径大（§8）
- 语义重构的风险在**名字**——字符串形式的耦合无处不在，`grep` 找不到的地方（反射、配置、外部系统按字符串引用的标识符）会静默损坏

> [!IMPORTANT]
> **本节的硬前提：没有行为基线与术语表，不许做语义级改动。**
> 本节只定义**安全规则**，不定义方法论；完整流程（行为冻结 → 语义审计 → 目标模型与命名归一 → 架构重划 → 分批迁移）见姊妹技能 `project-rearchitecture`。

---

### §9.1 语义级前置条件（在改任何一个名字之前，全部必须为真）

- [ ] **行为基线存在且当前全绿。** 至少有一份可重放的 `BEHAVIOR-CONTRACT.md`（见 `../../project-rearchitecture/references/behavior-freeze.md` 与 `templates/BEHAVIOR-CONTRACT-template.md`）。`KNOWN-FAILING` 段允许存在，但必须已逐条记录。
- [ ] **术语表存在。** `GLOSSARY.md` 中每个待改动的概念都有一句话定义 + 关键不变量 + 权威定义位置（`文件:行`）。
- [ ] **语义地图存在。** `SEMANTIC-MAP.md` 能回答"这个概念落在哪些代码上"，而不是靠临时搜索拼凑。
- [ ] **重命名映射已产出并获确认。** `RENAME-MAP.md` 写明旧名 → 新名、理由、影响面、契约处置，并经用户确认。
- [ ] **契约清点已完成。** 对外契约项（API 字段名、DB 表列名、事件 payload、错误码、CLI 参数、日志字段名）逐条标注为 `KEEP` / `BREAK-PLANNED`，且 **`UNKNOWN` 已收敛为零**。
- [ ] **这一批只做一类改动。** 「命名归一」与「结构重划」属于两个批次。

**任何一项为假 → 停下来，先补齐，再继续。**

> 理由与 §1「前置条件」是同一条：没有基线，你无法证明"功能没变"；没有术语表，你无法证明"改对了名字"。两者叠加之后，你甚至无法区分是改名改错了还是结构改错了。

---

### §9.2 语义红线 —— 停下来先询问

以下情形在做任何改动之前都需要用户明确确认：

**无行为基线就改语义或命名**
哪怕只是"把 `user` 统一成 `account`"。*为什么：* 没有基线时，改名引发的连锁失败无法与既有失败区分。改名是最容易被当成"零风险"的操作，而它恰恰最容易静默打断调用方。

**未清点对外契约就重命名**
未逐条确认 API 字段名、DB 列名、事件 payload、错误码、CLI 参数、日志字段名是否受影响，就动手改名。*为什么：* 契约项按字符串被外部消费，仓库内 grep 不到边界——照 §3「序列化格式变更」的红线对待。

**破坏性变更缺四件套中的任何一件**
版本提升 / 迁移脚本 / 弃用期 / 回滚步骤，**缺一不可**。*为什么：* 少任何一件，"支持破坏性变更"就退化为"悄悄破坏"。

**同一批次混合「命名归一」与「结构重划」**
例如一边把 `OrderV2` 改名，一边把订单逻辑搬进领域层。*为什么：* 两类改动各自都会失败，混在一起后失败原因不可分辨，回滚粒度也不再独立——一批必须是一个可独立验证、可独立回滚的变更集。

**删除疑似幽灵概念但未完成全量引用搜索**
搜索范围必须覆盖动态引用、反射、路由注册、事件订阅、配置、CI 脚本、文档（完整清单见 §9.5）。*为什么：* 幽灵概念的"零调用点"是 `grep` 的结论，不是事实；用字符串拼出来的调用点 grep 不到。

**DB 列名 / 表名重命名没有回滚脚本**
即使已经写了迁移脚本。*为什么：* 数据迁移是最难回滚的一类操作，失败常常在处理到一半时才暴露；没有回滚脚本就只能向前修数据。

**`UNKNOWN` 契约项未收敛就进入执行**
`BEHAVIOR-CONTRACT.md` 中仍有 `UNKNOWN` 的契约项。*为什么：* `UNKNOWN` 意味着"我还不知道改名会不会炸"。带着未知去改，等于拿生产验证猜测。

---

### §9.3 语义黄线 —— 警告并获得同意后继续

明确说明风险，等待用户确认后再继续：

| 情形 | 应给出的警告 |
|---|---|
| 一次重命名影响超过 20 个调用点 | "这次重命名涉及 M 个文件中的 N 个调用点。我会全部更新，但超过 20 个调用点的改动容易漏改。确认吗？" |
| 跨模块合并概念（两个模块各自的概念合成一个） | "这会把 A 模块的 X 与 B 模块的 Y 合并为一个概念。若它们其实不同义，这次合并会掩盖一个 D1。请确认它们真的指同一件事。" |
| 把「同义不同名」合并为一名 | "我会把 X / Y / Z 统一为 X。别名 Y / Z 将从代码中消失——下游若按字符串引用过它们，会静默损坏。" |
| 修改错误信息文案（可能被下游解析） | "这些文案可能被下游按字符串匹配（测试、告警规则、前端映射）。我会保持错误码不变，只改文案。确认吗？" |
| 调整日志字段名 | "日志字段名可能被仪表盘、告警与日志查询引用。改名会让既有查询静默返回空结果。请确认下游已同步。" |
| 重命名被外部系统按字符串引用的标识符 | "该标识符出现在跨系统约定的字符串中（队列名、topic、配置键、事件类型、环境变量）。仓库内找不到它的调用方。确认外部已同步吗？" |

### §9.4 重命名安全协议

任何重命名按顺序走完四步，**不要跳步**。

**步骤 1：统计调用点数量（先数，再决定）**

```
# 单符号统计（含定义处，记得扣除）：
grep -rn "symbolName" .
grep -rc "symbolName" . | grep -v ":0"        # 每个文件的命中数
# 命名风格不同时都要数（下划线 / 连字符 / 驼峰）：
grep -rniE "\bsymbol_?name\b|SymbolName" .
# 汇总文件数与调用点数：
grep -rl "symbolName" . | wc -l
grep -rn "symbolName" . | wc -l
```

| 调用点数量 | 判定 | 处置 |
|---|---|---|
| 1–20 | 可执行 | 按 §2 编辑前检查清单逐个更新 |
| **>20** | **黄线** | 先警告用户并获同意（§9.3），分批提交 |
| **>50** | **红线** | 停下来先询问；制定分批方案与弃用期，禁止一次性改完 |

**步骤 2：判定是否触及对外契约**

```
# 契约面搜索（逐个走一遍，不要只搜源码）：
grep -rn "symbolName\|symbol_name\|symbol-name" \
  openapi* swagger* *.proto *.graphql schema* migrations/ config/ *.yaml *.yml *.env* docs/
```

判定顺序（真值来源）：**数据形状 > DB schema > 对外 API > 领域层类型 > 使用频率最高者**，详见 `../../project-rearchitecture/references/semantic-audit.md` §1.5。

- **未触及** → 走内部改名，属于命名归一。
- **触及** → 这是**契约迁移**，不是重命名：按 §3 红线处理，并准备四件套（版本提升 / 迁移脚本 / 弃用期 / 回滚步骤）。

**步骤 3：决定是否需要别名过渡期**

需要别名过渡期的情况：

- 对面是不可控的消费方（外部系统、已发布的 SDK、移动端旧版本）
- 契约项判定为 `BREAK-PLANNED`，且无法与代码同步发布
- 调用点 >50，无法在一批内改完

写法：**新旧名并存，旧名委托给新名并标记弃用**，同时记录弃用期限与移除条件。

```
Step A — Alias:    新名生效，旧名作为别名转发（弃用注释 + 弃用期限）
Step B — Migrate:  内部调用点全部改用新名；测试同时覆盖两个名字
Step C — Contract: 确认无外部调用后删除旧名（这一步才动对外契约）
```

这与 §8.2 的三步序列同构：**引入 → 重定向 → 移除**。任何一步失败只回退那一步，不要向前修。

**步骤 4：执行后校验（缺一不可）**

- [ ] 静态检查通过（`tsc --noEmit`、`mypy`、`cargo check` 等）
- [ ] 行为基线全绿，`KNOWN-FAILING` 段与批次开始时一致
- [ ] 契约快照一致（未列入 `BREAK-PLANNED` 的契约项逐字节一致）
- [ ] 旧名残留为零（含注释、文档、配置、测试夹具）
- [ ] `RENAME-MAP.md` 已更新为"已执行"状态

### §9.5 幽灵概念删除协议

删除是**最难回滚的操作之一**。删除前必须完成本节全部步骤，且**单独一个批次**，不与任何其他改动混合。

**步骤 1：全量引用搜索（含易漏项）**

逐项确认，**每一项都要有搜索命令和结果记录**：

| 引用形式 | 搜索做法 |
|---|---|
| 静态源码引用 | `grep -rn "SymbolName" .` |
| 字符串形式的引用 | `grep -rn "\"SymbolName\"\|'SymbolName'" .` |
| 动态调用 / 反射 | `grep -rniE "(reflect|getattr|eval|invoke|getMethod|method_call)" .`，再按框架约定追 `Class::method`、`obj["method"]` 形式 |
| 路由注册 | `grep -rnE "(route|router|url|path)\(.*SymbolName" .` |
| 事件订阅 / 发布 | `grep -rnE "(on|subscribe|emit|publish|dispatch)\(.*SymbolName" .` |
| 依赖注入 / 容器注册 | `grep -rnE "(provide|bind|register|inject|component|bean)" .`，并逐项确认是否指向该符号 |
| 配置文件 | `grep -rn "SymbolName" *.json *.yaml *.yml *.toml *.ini config/` |
| CI / 构建脚本 | `grep -rn "SymbolName" .github/ .gitlab-ci.yml Makefile *.sh *.ps1 Dockerfile*` |
| 数据库对象 | `grep -rn "symbol_name" migrations/ schema*`；并直接查库确认表、列、视图、触发器、存储过程 |
| 文档 | `grep -rn "SymbolName" docs/ README* *.md` |
| 前端 / 客户端字符串 | `grep -rn "SymbolName" client/ web/ frontend/ mobile/ static/` |
| 序列化数据与快照 | `grep -rn "SymbolName" *.snap fixtures/ seeds/ data/ testdata/` |
| 特性开关与灰度配置 | 查开关平台 / 配置中心；**仓库外的部分必须问用户** |

> [!CAUTION]
> **`grep` 为零不等于无引用。** 任一项无法确认（外部系统、配置中心、运行时插件、动态注册）时，把它标为**未确认**并询问用户——不要默认"那就是没引用"。

**步骤 2：数据保留与合规检查**

- 相关表 / 字段是否仍有历史数据？有数据时**先归档再删**，不要直接 DROP。
- 是否存在合规保留要求（财务、审计、法务留存期）？
- 是否被正在运行的报表、对账、数据仓库同步任务引用？
- 删除后是否需要保留只读视图以兼容历史查询？

**步骤 3：可回滚性确认**

- 删除前记录当前 commit SHA，并确认整体可 `git revert`。
- 若含 DB 变更，回滚脚本必须**先写好并在副本库上演练过**。
- 明确写出回滚后的验证方式（怎么确认回滚成功）。

**步骤 4：独立批次 + 观察期**

单独提交、单独验证；删除后至少留一个观察周期（或用户指定的时长），再清理关联的配置与文档。

### §9.6 语义批次的回滚与信心标准

**与 §5 回滚协议的关系**

语义批次失败时同样执行 §5 的六步。额外两点：

1. **回退必须整体回退**——不能只回退"一半的改名"。命名归一要么全批生效、要么全部撤销，否则会留下新旧名混杂的中间态。
2. **同步回退 `RENAME-MAP.md`**，并把失败原因与批次号记进状态文件（见 `process.md` 的「长期项目协议」）。

**与 §7 信心等级的关系**

语义批次的每一步都要求 **High（高）** 信心。理由与 §8.6 相同，但侧重点不同：

- 架构重构的不确定来自"逻辑搬过去行为是否一致"
- 语义重构的不确定来自"这个名字还有谁在用，而且我搜不到"

因此：**当调用点统计不完备、或有任何契约项仍为 `UNKNOWN` 时，信心最高只能判为 Medium**——而 Medium 在语义批次里并不充分。停下来补齐搜索，或者问用户。

**语义批次「完成」的判定标准（全部为真才算完成）**

- [ ] **基线全绿。** 行为基线全部通过；`KNOWN-FAILING` 段与批次开始时一致，无新增失败。
- [ ] **契约快照一致。** 所有 `KEEP` 契约项逐字节一致；所有 `BREAK-PLANNED` 项已按四件套执行并留痕。
- [ ] **无残留别名。** 旧名在源码、配置、文档、测试夹具中均已清零；若仍处于弃用期，则弃用期限与移除条件已落盘且可追踪。
- [ ] **映射表已收口。** `RENAME-MAP.md` 中本批条目全部标记为已执行，`GLOSSARY.md` 与 `SEMANTIC-MAP.md` 已同步为新名。
- [ ] **状态已落盘。** `REARCH-STATE.md` / `AUDIT-PROGRESS.md` 已更新，下一批的入口已写明。
- [ ] **无夹带。** diff 中不含任何结构改动、行为修正或"顺手"的清理。

任一项为假 → 该批次**未完成**，不要开始下一批。
