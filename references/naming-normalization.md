# 阶段 2B：命名归一（Naming Normalization）

> 输入：阶段 1 的 `GLOSSARY.md` + `DRIFT-REPORT.md`，阶段 2A 的 `TARGET-MODEL.md`
> 输出：`RENAME-MAP.md`（旧名 → 新名 → 影响面 → 契约处置）
> **先定词，再动代码：动代码从阶段 3 开始。**

---

## §2B.0 三条不可动摇的分界

### 分界一：内部命名 ≠ 对外契约

必须把改名分成两类，处置方式完全不同：

| 类别 | 范围 | 性质 | 处置 |
|---|---|---|---|
| **内部改名** | 类名、方法名、变量名、模块名、文件名、私有函数、内部类型 | **纯重构** | 直接改，跑基线即可 |
| **契约改名** | API 路径与字段名、DB 表列名、事件 payload 字段、错误码、CLI 参数、日志字段名 | **契约迁移** | 必须走 [migration.md](migration.md) 四件套 |

> [!CAUTION]
> 把内部改名误判为契约改名，只是多花点功夫做迁移；
> 把契约改名误判为内部改名，会静默破坏下游系统——而且往往在部署后才被发现。
> 拿不准时，按契约改名处理。

### 分界二：改名 ≠ 结构改动

以下操作**不是改名**，它们改变了代码结构，必须独立成批：

- 把「名实不符」的方法里的副作用抽出去（D3 的拆解步骤）
- 为「缺失概念」引入新类型/值对象（D5）
- 拆分一个承担了多个概念的类（D1 的拆解步骤）
- 建立层级边界或移动文件

**绝对不允许**在同一个批次里既改名又改结构。原因：一旦基线失败，你无法判断是
命名问题还是结构问题，回滚粒度也会变得不可控。

### 分界三：改名必须是原子的，不要留过渡态

与契约改名（需要别名过渡期）相反，**内部改名不留别名**。
不要写 `class Customer extends OldAccountName` 这类兼容垫片，也不要保留 `@deprecated` 的转发方法。
内部改名的正确做法是**一次性把全部调用点改完**，中间不留任何双名共存状态。

理由：内部双名共存会让阶段 1 建立的语义地图立刻失效，后续审计会读到两个名字并再次困惑——
你等于重新制造了一遍 D2 漂移。

## §2B.1 产出 `RENAME-MAP.md` 的流程

### 步骤 1：从漂移清单提取改名任务

只处理这三类漂移会产生改名：**D1 同名不同义**（拆）、**D2 同义不同名**（并）、
**D3 名实不符**（拆副作用后再改）。
D4 幽灵概念走删除流程，D5 缺失概念走新增抽象流程，都不进 `RENAME-MAP`。

### 步骤 2：为每个概念确定唯一的内部主名

依据 `GLOSSARY.md` 中的「计划统一为」字段。真值来源判定顺序（来自
[semantic-audit.md](semantic-audit.md) §1.5）：

```
数据形状 > 数据库 schema > 对外 API > 领域层类型 > 使用频率最高的名字
```

命名风格必须**与项目现有风格一致**（`snake_case` / `camelCase` / `PascalCase`），
不要借重架构之机引入新的命名规范——那会制造一大批与语义无关的 diff，淹没真正的改动。

### 步骤 3：统计影响面

对每个待改标识符，统计调用点数量与被引用的文件数：

```
# 语言无关的近似统计（按词边界匹配，避免子串误伤）
grep -w "OldName"          # 统计命中行数
grep -rlw "OldName"        # 统计命中文件数
```

**必须同时检查这些易漏位置**：

- 字符串形式的动态引用（`getattr(obj, "OldName")`、`obj["OldName"]`、反射、依赖注入容器注册）
- 序列化/反序列化（JSON field、ORM 映射、GraphQL schema、DTO 转换）
- 配置与模板文件、SQL 字符串、前端模板
- CI/CD 脚本、Docker、运维脚本
- 文档与注释中的引用（不影响运行，但影响一致性）

### 步骤 4：判定契约处置

对每个待改标识符逐条判定：

| 判定 | 含义 | 动作 |
|---|---|---|
| `INTERNAL` | 不触及任何契约 | 直接改，跑基线 |
| `CONTRACT-BREAK` | 触及 API/DB/事件/错误码/日志 | 进 [migration.md](migration.md)，需要四件套 |
| `CONTRACT-KEEP` | 触及契约但决定保持不变 | **只改内部名，契约名保留** |

`CONTRACT-KEEP` 是最常见的正确结论。典型场景：DB 列 `cust_id` 很难改，
但内部代码可以统一叫 `Customer`，在映射层做转换。

### 步骤 5：批次编排

批次划分规则，按优先级：

1. **先小后大**：影响面 <5 个文件的重命名先做。它能验证你的基线是否真的可靠——
   如果第一个批次基线就抓到问题，说明基线有效；
   如果基线全绿但你明知改错了地方基线却没反应，说明基线有洞，必须先补。
2. **先独立后耦合**：只被单个模块引用的标识符先改；跨模块共享的后改。
3. **同概念成批**：同一个概念的全部别名在**同一批次**内改完。
   跨批次改同一个概念会留下中间态，制造新的 D2 漂移。
4. **契约变更单独成批**：`CONTRACT-BREAK` 项不与内部改名混批，因为有弃用期和
   外部协调成本，节奏完全不同。
5. **每批次上限**：建议单批次不超过 20 个文件改动，确保 diff 能在 2 分钟内评审完。

## §2B.2 `RENAME-MAP.md` 结构

模板见 [templates/RENAME-MAP-template.md](../templates/RENAME-MAP-template.md)。最小字段：

| 字段 | 说明 |
|---|---|
| 概念 | 关联 `GLOSSARY.md` 的概念名 |
| 旧名 | 当前代码中的标识符 |
| 新名 | 统一后的内部标识符 |
| 位置 | 定义位置（文件:行） |
| 调用点 | 数量 + 文件数 |
| 易漏引用 | 动态/序列化/配置/脚本中是否出现 |
| 契约处置 | `INTERNAL` / `CONTRACT-BREAK` / `CONTRACT-KEEP` |
| 批次 | 归属批次号 |
| 状态 | 待处理 / 进行中 / 已完成 / 已回滚 |

## §2B.3 D1 同名不同义的拆解流程

**危险度最高的一类，必须最谨慎。**

1. **确认两者确实无关**：检查它们是否读写同一批字段、是否在同一事务中、
   是否可互相赋值。若有关联，可能不是 D1 而是阶段 1 判错了，回去修正。
2. **决定保留哪个名字**：保留更贴合原语义的那个，另一个改名。
   若两者都不合适，两个都改名。
3. **决定拆解顺序**：若两者当前在同一个类/模块中，先**结构拆分**（独立批次），
   再分别改名（另一批次）。不要试图一次完成。
4. **改完后验证**：重新 grep 旧名，确认零残留；重新检查语义地图，
   确认两个新名字各自的引用范围与预期一致。

> [!WARNING]
> D1 的典型陷阱：改了「明显的那个」，忘了另一个「看起来不相关但用了同一个名字」的地方。
> 因此 `grep -rw` 的**全仓库结果必须逐条看过**，不能只看第一个模块的结果。

---

## §2B.4 D2 同义不同名的合并流程

1. **选定主名**（§2B.1 步骤 2）。
2. **为旧名建立完整清单**：把该概念的所有别名一次列全。
   `GLOSSARY.md` 的「当前代码中的名字」字段应已包含，若不全则回到阶段 1 补。
3. **一次性合并**：同一概念的所有别名在**同一批次**改完（见 §2B.1 步骤 5 规则 3）。
4. **注意语义细分**：有些「同义不同名」其实有细微语义差别
   （`user` 是账号、`customer` 是付费主体）。此时不是 D2 而是 D1，
   不要强行合并——**强行合并会丢失真实存在的语义区分**。

## §2B.5 执行方式

### 首选：codemod / 结构化重命名

按语义（符号引用）而非文本替换来改，能避免注释与字符串被误改。

| 语言 | 工具 |
|---|---|
| TypeScript/JavaScript | `ts-morph`、IDE 的 rename symbol、`jscodeshift` |
| Python | `rope`、`bowler`、IDE 的 rename |
| Java/Kotlin | IDE 的 rename、`OpenRewrite` |
| C# | Roslyn、IDE 的 rename |
| Go | `gopls rename`、`gorename` |
| Rust | `rust-analyzer` 的 rename |
| 其他/跨语言 | 先用 `grep -wl` 出文件清单，再逐文件人工改 |

### 禁止：全局文本替换

```
# 危险做法（会误改注释、字符串、无关子串、文档）
sed -i 's/OldName/NewName/g' $(git ls-files)
```

只有在**确认该名字在仓库中唯一且无字符串引用**时才允许文本替换，
且替换后必须逐条 review diff。

### 每批次执行循环

沿用 `references/process.md` 的执行循环，并叠加语义检查：

1. 记录批次开始前的 git commit（回滚锚点）。
2. 执行改名。
3. **语法/类型检查**：`tsc --noEmit` / `cargo check` / `mypy` / `go build ./...`。
4. **残留检查**：`grep -rw "OldName"` 必须零命中（或仅命中已声明的 `CONTRACT-KEEP` 位置）。
5. **跑行为基线**。
6. **契约快照校验**（若批次涉及契约相关代码路径）：确认对外契约未变。
7. 基线绿 → 提交，更新 `RENAME-MAP.md` 状态与 `REARCH-STATE.md`。
8. 基线红 → 回滚到步骤 1 的锚点，记录失败原因，拆小批次重试。

## §2B.6 命名风格细则

项目内已存在的约定优先于任何外部规范。

| 场景 | 规则 |
|---|---|
| 领域概念 | 用业务语言，不用技术语言。`Invoice` 优于 `BillingDataObject` |
| 避免技术后缀 | `Manager` / `Helper` / `Util` / `Handler` / `Processor` 多为命名无力，能换则换 |
| 布尔命名 | `is/has/can/should` 前缀，且**不要用否定形式**（`isNotReady` 改为 `isPending`） |
| 方法命名 | 动词短语；读操作与写操作要在名字上可区分（`get` vs `update`） |
| 集合命名 | 复数；单个元素用单数 |
| 缩写 | 项目内统一（不要一处 `usr` 一处 `user`） |
| 时间字段 | 明确单位与时区，`createdAt` 优于 `createTime`（视项目既有风格） |

> [!NOTE]
> 命名规范问题单独列进 `DRIFT-REPORT.md` 作为后续项，不与语义修正混在同一批。

---

## §2B.7 完成标准

1. `RENAME-MAP.md` 覆盖全部 D1/D2/D3 漂移项，无遗漏。
2. 每个标识符的影响面已统计（调用点数、文件数、易漏引用已检查）。
3. 每条已判定契约处置，且 `CONTRACT-BREAK` 项已有迁移方案。
4. 批次已编排，顺序符合 §2B.1 步骤 5 的规则。
5. 用户已确认 `RENAME-MAP.md`。

### 反模式清单

- ❌ 只统计 `grep` 命中的第一个模块就开始改
- ❌ 在一个批次里既改名又抽接口
- ❌ 内部改名留兼容别名
- ❌ 把 D1 当成 D2 强行合并，丢掉真实语义区分
- ❌ 用全局 sed 替换后不逐条 review
- ❌ 基线红了「顺手更新一下测试」
- ❌ 改完不 grep 旧名确认零残留

下一步：读 [migration.md](migration.md) 处理 `CONTRACT-BREAK` 项，
然后按批次进入阶段 3/4 执行。
