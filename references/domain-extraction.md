# 阶段 2A：领域模型与边界切分（Domain Extraction）

> 输入：阶段 1 的 `GLOSSARY.md`、`SEMANTIC-MAP.md`、`DRIFT-REPORT.md`
> 输出：`TARGET-MODEL.md`（目标领域模型 + 模块边界）
> **本阶段仍然不改业务代码。**

阶段 1 回答「有哪些概念」。本阶段回答「这些概念该怎么组织成模块与层次」。

---

## §2A.1 起点：从数据聚合而不是目录结构出发

AI 生成项目的目录结构通常是**事后归类**的产物（`utils/`、`services/`、`helpers/`
里各装一点），与真实语义边界不一致。因此**不要从目录推断边界**。

正确起点是阶段 1 已经拿到的**数据聚合**。做法：

1. 列出所有表/集合/持久化结构。
2. 对每张表，找出读写它的全部代码位置（阶段 1 已有部分数据，此处补全）。
3. 把「经常被同一批代码一起读写」的表聚成一组。
4. 每一组表 ≈ 一个**候选限界上下文（bounded context）**。

```
# 建立「表 → 代码」索引的核心搜索
grep: FROM <table>|INTO <table>|UPDATE <table>|\.<table>\.|model\(.*<Table>|@Entity.*<Table>
```

**判定标准**：两张表如果是同一个事务的不变量的一部分（要么一起改，要么都不改），
它们属于同一上下文；如果只是外键关联但各自独立变更，它们可以分属不同上下文。

---

## §2A.2 内聚判据：什么该合在一起

对任意两个候选概念，按下列判据打分。判据满足越多，越应该在同一模块内：

| 判据 | 说明 | 权重 |
|---|---|---|
| **共享不变量** | 存在一条约束必须同时对两者成立（例如「订单总额 = 明细合计」） | 最强 |
| **同一变更原因** | 业务规则变化时两者同时需要改 | 强 |
| **同一事务边界** | 必须在同一事务中读写 | 强 |
| **单向依赖** | A 需要 B 的信息，B 不需要 A 的信息 | 中 |
| **共享标识符** | 用同一个 ID 关联，且该 ID 在此处是主身份 | 中 |
| **仅外键关联** | 只靠外键相连，各自独立演进 | 弱（倾向分开） |
| **仅命名相似** | 名字像一个族，但没有数据/调用耦合 | **无效判据，必须忽略** |

> [!WARNING]
> **「仅命名相似」是审计中最常见的误判来源，也是 AI 生成项目的典型陷阱。**
> `UserService` 与 `UserReportService` 可能完全不相关；
> `OrderHelper` 里可能装着与订单无关的库存逻辑。
> 命名是线索，不是证据——这条纪律在阶段 1 已经强调过，此处是它最容易破功的地方。

---

## §2A.3 耦合形态判定

切边界前先判定当前的耦合形态，因为它决定切分策略的难度：

| 形态 | 特征 | 切分难度 | 应对 |
|---|---|---|---|
| **消息耦合** | A 调用 B 的方法，参数是简单值 | 低 | 直接抽接口 |
| **对象耦合** | A 持有 B 的对象引用并访问其内部 | 中 | 先封装，再抽接口 |
| **数据耦合** | A 与 B 共享数据库表 | 高 | 先确立表的归属，另一方改为通过接口访问 |
| **控制耦合** | A 通过标志参数控制 B 的行为分支 | 中 | 用多态/策略取代标志参数 |
| **公共耦合** | A 与 B 共享全局可变状态 | 最高 | 先消除全局状态，再切分 |
| **内容耦合** | A 直接修改 B 的内部字段 | 高 | 先加封装边界 |

**切分顺序原则：先易后难。** 从消息耦合开始建立边界，最后处理数据耦合与公共耦合。
反过来做会立刻陷入无法验证的状态。

## §2A.4 分层目标的选择

不要默认套用 Clean Architecture。按项目实际情况选择，并**明确写下选择理由**：

| 目标 | 适用条件 | 代价 |
|---|---|---|
| **不引入分层，只做命名归一 + 内聚整理** | 项目小、变更不频繁、无多端需求 | 最低。经常是正确选择 |
| **轻量三层：接口层 / 领域层 / 数据访问层** | 业务规则开始复杂，但仍是单一交付形态 | 中 |
| **Clean Architecture / 六边形** | 多端接入、需要替换基础设施、领域规则复杂且有测试价值 | 高。需要大量接口与依赖倒置 |
| **按限界上下文拆分模块（不引入技术分层）** | 多业务域混杂在一个进程里，域之间几乎无耦合 | 中 |
| **拆分为独立服务** | 已有独立部署诉求、团队边界明确 | 最高。不是重构而是分布式化 |

> [!IMPORTANT]
> **「功能不变」是硬约束，因此拆分为独立服务通常超出本技能的适用范围。**
> 本技能允许把代码在进程内按上下文重新组织，但不承担分布式化带来的
> 一致性、事务、网络故障等新问题。若用户要求拆服务，明确告知这是架构演进而非重构。

**空领域层特别说明**：如果阶段 1 发现代码是「扁平化 handler」（业务规则全在控制器/路由里），
目标不是立刻建立完整分层，而是**先把规则从 handler 中提炼出来，放进领域层**。
这一步按 `references/catalog-composing.md` 的提取手法执行，
属于**结构改动批次**，与命名归一分开。

## §2A.5 契约映射（最容易被忽略的一步）

目标模型确定后，必须逐条回答：**每个目标模块负责哪些对外契约点？**

| 目标模块 | 负责的 API 路径 | 负责的表 | 负责的事件/topic | 负责的错误码 |
|---|---|---|---|---|
| | | | | |

这一步的价值有两个：

1. **发现归属冲突** —— 某个 API 路径涉及的字段来自三个不同模块，说明边界切错了，
   或者该 API 的输出本身就是一个需要重新设计的契约。
2. **为迁移做准备** —— 阶段 4 的破坏性变更必须按模块成批下发，没有这张表就无法编排。

> [!CAUTION]
> 如果发现某个契约点**无法归属于任何模块**，不要随便塞进去。
> 这通常意味着存在一个还没被识别的概念（回到阶段 1 的 D5 缺失概念处理），
> 或者该契约本身就是历史遗留的拼接产物，需要单独决策。

## §2A.6 目标模型文档

产出 `TARGET-MODEL.md`，模板见
[templates/TARGET-MODEL-template.md](templates/TARGET-MODEL-template.md)。必须包含：

1. **限界上下文清单** —— 每个上下文的名称、职责一句话、包含的概念、负责的契约点。
2. **上下文之间的依赖方向** —— 必须是**有向无环图**。若出现环，说明边界切错了。
3. **核心域 / 支撑域 / 通用域的划分** —— 决定投入优先级。
4. **分层选择与理由** —— 明确写出为什么选这个目标（照 §2A.4 论证）。
5. **目标模块 → 当前代码的映射** —— 现有文件将来归入哪个模块。
   这份映射是阶段 3 与阶段 4 的施工图。
6. **不处理范围** —— 明确列出本次不动的东西（尤其阶段 0 护栏里无基线覆盖的区域）。

### 依赖方向检查

```
# 用导入关系验证是否有环（语言无关的近似做法）
grep: ^import |^from |require\(|use crate|using 
```

对目标模型验证：

- [ ] 上下文依赖图无环
- [ ] 核心域不依赖任何支撑域/通用域的实现细节（只依赖接口）
- [ ] 通用域不依赖业务域
- [ ] 每个契约点恰好归属一个模块
- [ ] 阶段 1 的每条漂移都能在目标模型里找到归宿（改名、迁移、或明确不处理）

---

## §2A.7 完成标准

阶段 2A 完成的标志：

1. 能画出上下文依赖图，且无环。
2. 每个目标模块有明确职责与契约点归属。
3. 分层选择有书面理由，不是抄模板。
4. 目标模块 → 现有代码的映射完整，没有「以后再说」的孤儿文件。
5. `TARGET-MODEL.md` 已提交，并已经过用户确认。

**用户确认是硬性要求。** 目标模型是后续所有改动的蓝图，理解偏差会在阶段 3–4 被放大
成大量返工。

下一步：读 [naming-normalization.md](naming-normalization.md) 把术语落到代码上。
若目标模型要求破坏对外契约，同时读 [migration.md](migration.md) 准备方案。
