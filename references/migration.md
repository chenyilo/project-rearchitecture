# 阶段 4：破坏性变更与迁移（Migration）

> **允许破坏对外契约，但绝不允许无迁移的破坏。**
> 破坏性变更的四件套缺一不可：**版本提升、迁移脚本、弃用期、回滚步骤**。

---

## §4.1 什么算破坏性变更

对照阶段 0 的 `BEHAVIOR-CONTRACT.md` 逐条判定。以下都算破坏，包括看似无害的那些：

| 层 | 破坏性变更示例 |
|---|---|
| **L1 对外交互面** | 删除/重命名 API 路径或字段；改变字段类型；改变必填性；改变默认值；改变状态码语义；删除 SDK 公共方法 |
| **L2 数据契约** | 重命名表/列；改变列类型或精度；加非空约束；删列；改索引唯一性；改缓存 key 结构；改消息体字段名 |
| **L3 集成契约** | 改鉴权形态；改签名算法；改回调 payload；改第三方调用的参数语义 |
| **L4 可观测行为** | 改错误码；改错误信息文案（下游可能按字符串解析）；改日志字段名（告警规则可能依赖）；改指标名；改健康检查路径 |

> [!CAUTION]
> **L4 的破坏性最常被低估。** 换个错误文案、重命名一个日志字段，
> 就足以让运维的告警规则静默失效——而且不会报错，只会在出事那天才发现。
> 判定 L4 时，去检查一下告警规则、日志解析脚本、仪表盘配置。

### 三选一，必须明确

对每个契约点，最终只能落在：

- `KEEP` —— 不改。内部代码通过映射层适配（推荐优先考虑）。
- `BREAK` —— 改。**必须**配齐四件套。
- `UNKNOWN` —— 不允许带入本阶段。回阶段 1/2 收敛。

---

## §4.2 三道闸：Expand → Migrate → Contract

任何破坏性变更都拆成三个独立批次。**它们的顺序不可颠倒，也不可合并。**

### 闸 1：Expand（扩展）

**目标**：让新旧两套形态**同时可用**。此阶段不删除任何东西。

- API：新增新字段/新路径，旧的在，两者都能用。
- DB：新增新列，旧列保留（或新增视图做映射）。
- 事件：payload 同时包含新旧字段。
- 代码：新增适配层，把内部分别映射到两套外部形态。

**完成判据**：旧调用方零感知，新调用方已可用。基线全绿。

### 闸 2：Migrate（迁移）

**目标**：把使用方从旧形态迁到新形态，并回填数据。

- 数据回填脚本（见 §4.4），幂等、可重入、可回滚。
- 下游调用方逐个切换（见 §4.5 的编排）。
- **双写期间**同时写新旧两处，并在比对中验证一致。
- 监控新路径的使用量，直到旧路径使用量归零。

**完成判据**：旧形态使用量为零（有监控证据，不是靠猜），新旧数据一致。

### 闸 3：Contract（收缩）

**目标**：删除旧形态。

- 删除旧 API 字段/路径、旧列、旧事件字段、适配层。
- 这一步**必须等待弃用期结束**（§4.3 四件套之三）。

**完成判据**：旧形态完全消失，基线绿，契约文档已更新。

> [!IMPORTANT]
> **同一时间只推进一个闸。** 三个闸并行是事故的常见成因——
> 收缩没完成时又开始下一轮扩展，旧形态会被误删。

---

## §4.3 破坏性变更四件套

缺任何一件，都不得开始执行。

### 之一：版本提升

| 变更类型 | 版本策略 |
|---|---|
| HTTP API | URL 版本（`/v2/`）或 header 版本；小改动用字段级弃用标记 |
| SDK / 库 | 遵循语义化版本，主版本号提升 |
| 事件/topic | 新增 topic 版本（`orders.created.v2`），而不是原地改 |
| DB schema | 迁移文件编号递增；记录在迁移历史中 |
| CLI | 大版本提升；必要时保留旧参数一个版本 |
| 日志/指标 | **不做版本管理**，因此改这些必须走显式确认 + 通知运维 |

### 之二：迁移脚本

必须满足：

- **幂等**：重复执行结果一致。
- **可重入**：中断后可继续，不需要人工清场。
- **分批**：大数据量时按主键区间/时间窗口分批，避免长事务锁表。
- **有 dry-run**：先输出「将影响多少行/多少条记录」，经确认再真正执行。
- **有进度与日志**：能知道跑到哪了。
- **可回滚**：配对应的反向脚本（见之四）。

### 之三：弃用期

- 明确写下**结束日期**，不能写「以后」。
- 在 Expand 阶段就发出弃用通知：旧形态返回 deprecation 警告（header、日志、告警）。
- 监控旧形态使用量，作为能否进入收缩闸的**客观依据**。
- 弃用期长度按调用方数量与协调难度决定；**没有监控数据就不许进收缩闸**。

### 之四：回滚步骤

- 逐步写清：回滚命令、执行人、判定条件（什么现象下必须回滚）。
- **数据变更的回滚最难**：删列/删表的回滚需要备份或反向脚本。
  执行前必须有备份，且**验证过备份可恢复**（不是「备份了就算」）。
- 明确写出**不可回滚的点**（例如数据已按新格式被外部消费）。
  这类点必须提前告知用户并获得确认。

## §4.4 数据迁移专项

### 顺序

```
1. Expand   新增新列（可空）       ← 不动旧列
2. 双写     代码同时写新旧列        ← 灰度开启
3. 回填     历史数据补齐新列        ← 幂等、分批、可重入
4. 校验     新旧列逐条比对          ← 差异必须为 0
5. 切换读   读路径改为读新列        ← 观察一段时间
6. 停止写旧 不再写旧列
7. Contract 删除旧列                ← 确认无任何读取后
```

**每一步都是独立批次，每步之后基线与数据校验都要过。**

### 回填脚本要求

```sql
-- 分批回填骨架（幂等 + 可重入）
UPDATE target_table
SET new_column = <映射表达式>
WHERE new_column IS NULL
  AND id > :last_id
ORDER BY id
LIMIT :batch_size;
-- 记录 last_id 到进度表，中断后可继续
```

- 映射表达式必须与业务规则一致；**规则有歧义时问用户，不要自行假设**。
- 遇到无法映射的行（脏数据），**记录下来而不是跳过或强行填默认值**。

### 校验要求

- 新旧值差异计数必须为 0 才算通过。
- 抽样人工核对关键字段（计数为 0 也可能两边都错）。
- 唯一性约束、外键完整性、非空约束都在新列上验证过。

### 危险清单

- ❌ 在业务高峰期做大表 DDL
- ❌ 单事务改全表
- ❌ 先删旧列再回填
- ❌ 回填脚本没有 dry-run
- ❌ 校验只看总行数不看值
- ❌ 没有备份就删列/删表

## §4.5 下游调用方编排

破坏性变更的前提是**知道谁在用**。

1. **清点调用方**：内部仓库、外部合作方、移动端旧版本、批量脚本、BI/报表、运维工具。
   移动端与外部合作方通常是最难协调的——它们不受你控制。
2. **逐个确认迁移时间表**，写进 `MIGRATION-PLAN.md`。
3. **无法协调的调用方**：若存在无法迁移的调用方（例如已发布的老版本 App），
   该契约点实际**不能破坏**——降级为 `KEEP` 并告知用户这个约束。
4. **灰度与观察**：新形态先小流量，观察错误率、延迟、下游反馈。
5. **保留兜底**：弃用期内旧形态必须仍然正确，不能「先坏着，反正快删了」。

## §4.6 批次编排与门禁

### 每个批次的必过关禁

1. 语法/类型检查通过
2. 行为基线全绿
3. **契约快照一致**：对 `KEEP` 的契约点，抓取改动前后的实际输出并 diff
4. 数据一致性校验通过（涉及数据时）
5. 旧形态使用量符合预期（Expand/Migrate 阶段应为增长，Contract 阶段应为零）
6. `MIGRATION-PLAN.md` 与 `REARCH-STATE.md` 已更新

### 批次顺序（全局）

```
批次 N    内部命名归一（纯重构，无契约风险）        ← 先做，建立信心与干净基线
批次 N+1  结构改动（命名已稳定）
批次 N+2  契约破坏 · 闸1 Expand
批次 N+3  契约破坏 · 闸2 Migrate + 回填
批次 N+4  契约破坏 · 闸3 Contract
```

**先把内部改完再动契约**，理由：内部改名能立刻验证基线是否可靠、语义地图是否准确；
带着错误的语义地图去做破坏性变更，风险会被放大数倍。

### 不可回滚点必须显式声明

在 `MIGRATION-PLAN.md` 中单列一节，列出所有「过了这一步就回不去」的点，
以及每个点的判定条件与用户确认记录。

---

## §4.7 完成标准

1. 每个 `BREAK` 契约点都配齐四件套，且逐条可查。
2. 三道闸按顺序执行完毕，无跳过。
3. 弃用期已结束（有监控证据），旧形态已完全删除。
4. 数据迁移已校验，差异为 0。
5. 基线全绿，契约快照与新的目标契约一致。
6. 文档已更新：`BEHAVIOR-CONTRACT.md` 反映新契约、`GLOSSARY.md` 已冻结、
   `MIGRATION-PLAN.md` 归档。
7. 不可回滚点已向用户明确说明并获得确认。

下一步：回到 [session-state.md](session-state.md) 更新状态，
按 `RENAME-MAP.md` 与 `MIGRATION-PLAN.md` 推进下一个批次。
