# 跨会话状态管理（Session State）

> [!IMPORTANT]
> **聊天记录不是状态，仓库里的文件才是状态。**
> 一次会话装不下 100+ 文件的语义地图。所有进展都必须落在版本化文件里，
> 使得任何一次新会话都能在**不读历史对话**的前提下从断点继续。

适用范围：项目 >100 文件、审计需要跨天／跨会话推进、或需要多人／多个 agent 并行时。
单会话能做完的小项目也要落盘，但可以只维护 `REARCH-STATE.md`。

---

## §2.0 为什么必须落盘

重架构的失败方式很少是「某一步改错了」，而更常见的是**进度蒸发**：

| 失效现象 | 后果 |
|---|---|
| 审计结论只留在对话里 | 下次会话重新审计同一批文件，结论还可能与上次冲突 |
| 不记得哪些切片已审 | 重复劳动 + 漏审（漏审的切片会在阶段 3 突然爆炸） |
| 不记得某批次为什么回滚 | 换个写法再踩同一个坑，浪费一到两轮 |
| 不记得「下一步从哪开始」 | 每次会话前 20% 的时间都花在重新定位上 |
| `UNKNOWN` 项散落在多段回复里 | 无法判断距离阶段 2 结束还有多远 |

上下文预算是硬约束：

- 每个切片的审计要读 5–20 个源文件，加上 `BEHAVIOR-CONTRACT.md` 与术语表，
  一次会话的可用于「真正思考」的预算通常只够**一个切片**。
- 上下文被塞满后，模型的输出会开始退化：结论互相矛盾、忘记纪律、顺手改代码。
  这不是可以通过「更努力」解决的问题，只能通过**把状态外置**解决。
- 因此默认工作模式是：**每次会话 = 开始协议 → 一个批次／一个切片 → 结束协议。**

> [!WARNING]
> 会话结束后只有仓库可读——接手的人可能是几天后的你，也可能是另一个 agent。

## §2.1 两个状态文件

职责严格分开。**不要试图用一个文件同时承担全局与逐切片两件事**——
它会在一周内变成一份没人维护的流水账。

| | `REARCH-STATE.md` | `AUDIT-PROGRESS.md` |
|---|---|---|
| 粒度 | 全局（阶段／批次级） | 逐切片（文件级） |
| 回答的问题 | 我现在做到哪一步？下一步做什么？ | 哪些切片审完了？各产出什么？ |
| 更新时机 | 每次会话结束、每个批次收尾 | 每完成一个切片立即更新 |
| 典型体量 | 1–2 屏，**能一眼看完** | 随切片数量增长，允许较长 |
| 模板 | [REARCH-STATE-template.md](../templates/REARCH-STATE-template.md) | 见 §2.6 的进度表格式 |

建议放在仓库根目录的 `docs/rearchitecture/` 下：

```
docs/rearchitecture/
├── REARCH-STATE.md          # 全局状态（本文件主责）
├── AUDIT-PROGRESS.md        # 逐切片进度
├── BEHAVIOR-CONTRACT.md     # 阶段 0 产出
├── GLOSSARY.md              # 阶段 1 产出
├── SEMANTIC-MAP.md          # 阶段 1 产出
├── DRIFT-REPORT.md          # 阶段 1 产出
├── TARGET-MODEL.md          # 阶段 2 产出
└── RENAME-MAP.md            # 阶段 2 产出
```

> [!NOTE]
> `REARCH-STATE.md` 必须保持**短**。当它超过两屏时，说明你把逐切片的细节写错了地方——
> 那些内容属于 `AUDIT-PROGRESS.md` 或 `DRIFT-REPORT.md`。

### 全局状态文件必须回答的六个问题

1. **当前阶段** —— 阶段 0/1/2/3/4 中的哪一个。
2. **当前批次** —— 批次的编号、目标、涉及切片、是否已开分支。
3. **已完成切片** —— 只列名字与产出文件的链接。
4. **待办与优先级** —— 下几个批次是什么，按什么排序。
5. **已知风险与坑** —— 已确认的雷区（例如「`billing` 目录里有一个假测试，不要信它」）。
6. **下一步入口** —— 具体到文件与批次，见 §2.3。

## §2.2 会话开始协议

**每次新会话的第一件事，不是看代码，是读状态。** 顺序不可调换。

```
步骤 1  读 REARCH-STATE.md          → 当前阶段、当前批次、下一步入口
步骤 2  读 AUDIT-PROGRESS.md        → 本批次涉及的切片审到哪了
步骤 3  读 BEHAVIOR-CONTRACT.md     → 哪些契约是 KEEP，基线怎么跑
步骤 4  跑一次行为基线              → 确认当前是绿的，再动任何东西
步骤 5  对账                         → 状态文件描述与代码现状是否一致
步骤 6  声明本次会话唯一目标         → 一个批次，或一个切片，不贪多
```

### 步骤 4：为什么必须先跑基线

基线不是「改完再跑」的东西，它是**会话的合法性前提**。如果进入会话时基线就是红的，
你无法区分后续失败是自己改坏的还是本来就坏的。

```bash
# 分层的子集运行（先从 BEHAVIOR-CONTRACT.md 抄命令，不要凭记忆写）
<子集基线命令>

# 记录本次会话开始时的基线状态，回头写进状态文件
git rev-parse --short HEAD
git status --porcelain
```

| 会话开始时基线的状态 | 处理 |
|---|---|
| 全绿 | 正常开始 |
| 有失败，且与 `KNOWN-FAILING` 清单一致 | 正常开始，清单本身是基线的一部分 |
| 有失败，但**不在** `KNOWN-FAILING` 里 | **停止**。先定位是环境问题还是上次会话留下的未提交改动 |
| 工作区有未提交改动，且不是上次会话声明的批次产物 | **停止**。先弄清这些改动是什么，不要在其上叠加新改动 |

### 步骤 5：对账

状态文件会与代码脱节。开始前花一分钟核对：

```bash
# 状态文件里记的 commit 现在还在吗
git log --oneline -n 20
git branch -a --contains <状态文件里记的 commit>

# 状态文件说「已完成」的批次，其产物文件是否真的存在
ls docs/rearchitecture/
```

发现脱节时：**以代码为准，修正状态文件**，并在「变更历史」里记一笔「为什么脱节」。

## §2.3 会话结束协议

> [!CAUTION]
> 会话结束协议不是可选项。**跳过它的收益是省 5 分钟，代价是下次会话多花一小时重新定位，
> 外加一次重复踩坑。**

结束前必须更新 `REARCH-STATE.md` 的下列内容：

1. **当前批次进展** —— 做到哪一步（改名映射已完成？代码改到第几个文件？测试跑了吗？）。
2. **下一步第一件事** —— 一句话，具体到文件与操作。
3. **踩过的坑** —— 本次发现的新雷区，写进「已知风险与坑」。
4. **未决问题** —— 新的 `UNKNOWN`／`UNRESOLVED` 项，含计数变化。
5. **变更历史** —— 加一行：日期、会话目标、结果（完成／部分／回滚）。

### 「下一步入口」必须具体到文件

判定标准：**一个完全没有上下文的 agent，只读这句话就能开始工作。**

| 反例（无效） | 正例（有效） |
|---|---|
| 「继续审计」 | 「审计切片 S4 `src/payment/`（17 个文件），从未读的 `refundHandler.ts` 开始」 |
| 「处理一下漂移」 | 「执行 DRIFT-REPORT.md 中 D2-07（`cart`→`order` 改名），改名映射已确认，待改 6 个文件」 |
| 「改剩下的部分」 | 「批次 B3 还剩 3 个文件未改：`a.ts:44`、`b.ts:12`、`c.ts:130`；改完跑 `npm run test:unit`」 |
| 「有测试挂了，回头看看」 | 「`test_order_total.py::test_discount` 挂了，怀疑与批次 B2 的改名有关，**已回滚** B2 的最后一步」 |

### 交接清单（会话结束时逐项打勾）

```markdown
- [ ] REARCH-STATE.md 的「当前批次」已更新到真实进展
- [ ] REARCH-STATE.md 的「下一步入口」已写成可执行的具体动作
- [ ] AUDIT-PROGRESS.md 已反映本次完成的切片（含产出文件路径）
- [ ] 行为基线已重跑，状态与 BEHAVIOR-CONTRACT.md 记录一致
- [ ] 本次新增的 UNKNOWN / UNRESOLVED 项已计数并落盘
- [ ] 本次踩的坑已写进「已知风险与坑」（含「不要再试的方向」）
- [ ] 状态文件与代码改动已提交（见 §2.5）
- [ ] 工作区干净，或遗留改动已在状态文件中明确声明
```

## §2.4 批次中断与回滚的状态记录

批次失败并回滚时，失败的记录能防止下一个人重走同一条路。

回滚后立即在 `REARCH-STATE.md` 的「已知风险与坑」中追加一段：

```markdown
### 失败批次：B2（订单模块命名归一）

- 日期：2026-03-14
- 目标：把 `cart` / `basket` / `tray` 统一为 `order`
- 失败点：改到第 4 个文件时 `test_checkout_flow` 挂了，基线红
- 现象：<具体错误输出，一行即可>
- 判定：<是回归？是基线本身没覆盖到？是漏改的动态引用？>
- 已执行：`git reset --hard <回滚到的 commit>`，工作区已干净
- **不要再试的方向**：<例如「不要直接改 DB 列名——该列被外部报表系统按名字读取」>
- 下次的替代方案：<例如「先加适配层读取，下个版本再契约化列名」>
```

> [!WARNING]
> 「不要再试的方向」这一栏**必须写**。没有它，下一个接手者（或三天后的你）
> 有很大概率用另一种写法再撞一次同一堵墙。

三条硬规则：

1. **回滚要落到具体 commit**，不能写「回滚了一部分」。
2. **回滚后必须重跑基线**并把结果写进状态文件——回滚也可能不干净。
3. **回滚的批次不删除记录**。它从「待办」移到「已验证不可行」。

## §2.5 状态文件与 git

### 提交时机

状态文件是文档，跟着代码一起走，**不要攒**：

| 时点 | 提交内容 | 提交信息示例 |
|---|---|---|
| 每个切片审计完成 | `AUDIT-PROGRESS.md` + 该切片产出的文档片段 | `docs(rearch): audit slice S3 (auth)` |
| 每个批次收尾 | `REARCH-STATE.md` + 代码改动 + 产出物 | `rearch(B1): unify customer naming` |
| 会话结束（无代码改动） | 仅状态文件 | `docs(rearch): session state after S4 partial` |
| 批次回滚后 | 状态文件（记录失败） | `docs(rearch): record B2 rollback + why` |

> [!NOTE]
> **每批次一个 commit，绝不要把多个批次揉进一个 commit。**
> 批次是「可独立回滚」的最小单位，提交历史必须与批次边界一一对应，
> 否则 `git revert` 会连带回滚掉另一个已完成的批次。

### 多分支／多工作树的并行推进

只有在**切片互不重叠、批次互不依赖**时才允许并行。否则并行会制造出最难解的一类冲突：
两个分支对同一概念给出不同命名，最后无法自动合并。

| 场景 | 做法 |
|---|---|
| 两个 agent 审不同切片 | 各自分支，只改自己切片的审计产物；`AUDIT-PROGRESS.md` 按切片行分段，冲突概率低 |
| 命名归一（阶段 2/3） | **串行**。命名是全局一致的，并行必然冲突 |
| 文档工作与代码工作并行 | 安全。文档分支与代码分支互不触碰 |
| 使用 git worktree | 推荐：`git worktree add ../repo-S4 -b rearch/S4`，每个切片独立工作目录，互不干扰 |

减少冲突的实际技巧：

```markdown
<!-- AUDIT-PROGRESS.md 中为每个切片预留固定区块，不同分支只改自己那块 -->
<!-- 不要重新排序表格行，不要「顺手整理」别人的区块 -->
```

`REARCH-STATE.md` 因为只有一份，并行时按「谁先合并谁写」处理：
合并时**以合并后的实际代码为准重写一次**，不要机械地解决冲突标记。

### rebase 后修正 commit 引用

状态文件里会记 commit 哈希（批次起点、回滚点、基线录制点）。**rebase / squash / amend
之后这些哈希全部失效**，必须修正：留着旧哈希会让人 checkout 到一个错误的树。

```bash
# rebase 之后重新定位：用提交信息而不是哈希来找
git log --oneline --grep="rearch(B1)" --all
git log --oneline --grep="record B2 rollback" --all

# 取修正后的短哈希
git rev-parse --short <匹配到的提交>
```

修正规则：

1. **优先用可搜索的标记**：提交信息里的批次号（`rearch(B1)`）比哈希稳定得多。
   新建批次时就在状态文件里同时记「哈希 + 批次提交信息前缀」。
2. rebase 后把状态文件里的全部哈希**逐条核对更新**，并在「变更历史」记一行
   「因 rebase 修正 commit 引用」。
3. 已经共享出去的分支**不要 rebase**；`REARCH-STATE.md` 的准确性依赖于历史不再被改写。
4. 回滚点的哈希必须**始终有效**（它是救命字段）。如果某个回滚点因 rebase 失效，
   立刻用 `git tag` 打一个不可变的标签替代：

```bash
git tag rearch-rollback-B2 <commit>   # 打标签，避免 rebase 影响
```

## §2.6 审计进度指标

用四个可数的指标回答「还剩多少工作」：

| 指标 | 定义 | 期望走向 |
|---|---|---|
| **已审计切片数 / 总切片数** | 切片分母在阶段 1 开始时定死，之后只允许因「发现新切片」而增加，并记录理由 | 单调递增至 1.0 |
| **`UNKNOWN` 计数** | 契约点中尚未判定为 KEEP / BREAK-PLANNED 的数量 | **必须在阶段 2 结束前收敛为 0** |
| **`UNRESOLVED` 计数** | 无法从代码判定语义的概念／漂移项数量 | 每条必须最终有处置：继续调研 / 问用户 / 列入不处理 |
| **漂移处置进度** | 已处置（改名／拆分／删除／引入概念）的漂移项 / 总漂移项 | 按优先级从高到低推进 |

> [!IMPORTANT]
> `UNKNOWN` 与 `UNRESOLVED` 都必须带计数出现在 `REARCH-STATE.md` 的「未决问题」段落里。
> 计数只增不减，说明审计在制造问题而没有收敛——这是需要立刻处理的信号。

### `AUDIT-PROGRESS.md` 的进度表格式

```markdown
| 切片 | 文件数 | 审计状态 | 产出文件 | `UNRESOLVED` | 遗留问题 |
|---|---|---|---|---|---|
| S1 `src/auth/` | 12 | ✅ 已完成 | GLOSSARY.md §核心域 | 0 | — |
| S2 `src/order/` | 19 | ✅ 已完成 | GLOSSARY.md §支撑域 | 2 | `tray` 的来源不明，待问用户 |
| S3 `src/billing/` | 8 | 🔄 进行中 | — | 1 | 第 5 个文件未读 |
| S4 `src/payment/` | 17 | ⬜ 未开始 | — | — | — |
| S5 `src/notify/` | 6 | ⬜ 未开始 | — | — | — |

**审计状态汇总**：已完成 2 / 5 ；`UNRESOLVED` 合计 3；预计剩余 3 个切片 ≈ 3 次会话
```

状态只允许四种取值：`⬜ 未开始`、`🔄 进行中`、`✅ 已完成`、`⛔ 受阻`。
「受阻」必须紧跟一句为什么受阻。**不要发明第五种状态**，例如「差不多完成」。

### 阶段进度看板（放在 `REARCH-STATE.md`）

```markdown
| 阶段 | 状态 | 完成判据 | 阻塞项 |
|---|---|---|---|
| 阶段 0 行为冻结 | ✅ | 基线一条命令可复现，UNKNOWN 已列出 | — |
| 阶段 1 语义审计 | 🔄 | 5 个切片全部有证据记录，漂移全部评分 | S3 未审完 |
| 阶段 2 目标模型 | ⬜ | UNKNOWN 收敛为 0，GLOSSARY 冻结 | — |
| 阶段 3 架构重划 | ⬜ | TARGET-MODEL 与边界确认 | — |
| 阶段 4 分批迁移 | ⬜ | 批次全部收尾，基线全绿 | — |
```

## §2.7 反模式清单

| # | 反模式 | 为什么有害 | 正确做法 |
|---|---|---|---|
| 1 | 状态文件里写**聊天摘要**（「今天讨论了订单模块，感觉有点乱」） | 摘要不可执行，无法据此继续工作 | 只写事实：切片名、文件路径、commit、结论、下一步动作 |
| 2 | 不记录**失败原因**与「不要再试的方向」 | 换个人原地重踩同一个坑 | 每次回滚都写失败点 + 判定 + 禁行方向（§2.4） |
| 3 | 状态文件与**实际代码脱节**（说已完成，其实没提交） | 下次会话在假进度上继续，产出全部作废 | 会话开始对账（§2.2 步骤 5）；结束前 `git status` 确认干净 |
| 4 | 把 `REARCH-STATE.md` 写成**流水账**（每个文件都记一行） | 没人读 → 等价于没有状态 | 全局文件保持 1–2 屏；细节下沉到 `AUDIT-PROGRESS.md` |
| 5 | 「下一步入口」写「继续」类模糊描述 | 下次会话前 20% 时间用于重新定位 | 必须具体到文件／批次／命令（§2.3 表格） |
| 6 | `UNKNOWN` / `UNRESOLVED` **只增不减也不解释** | 无法判断何时能进阶段 2 | 每次会话更新计数，只增不减时写明原因与收敛计划 |
| 7 | 多个批次**揉进一个 commit** | `git revert` 会连带回滚另一个已完成的批次 | 一批次一 commit，提交信息带批次号 |
| 8 | 在共享分支上 **rebase** 后不修 commit 引用 | 回滚点失效，出问题时找不到可用的树 | rebase 后逐条修正 + 关键回滚点打 `git tag` |
| 9 | 并行分支各自**独立命名归一** | 合并时概念冲突无法自动解决 | 命名归一串行；并行只用于互不重叠的切片审计 |
| 10 | 依赖「本次会话我会记得」 | 会话结束即遗忘，进度蒸发 | 一切结论落盘，落盘是唯一持久化机制（§2.0） |

> [!CAUTION]
> 反模式 3（状态脱节）和反模式 10（依赖记忆）是最常见的两种。
> 它们不会立刻报错，而是让下一次会话**在白费力气中度过**，
> 并且通常在你已经改了几十个文件之后才暴露。
