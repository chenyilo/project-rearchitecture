# 通用重构流程（Universal Refactoring Process）

无论使用何种语言、执行何种操作，每次重构会话都遵循本流程。各阶段按顺序推进——不要跳步。

---

## 阶段 1：信息收集（Intake）

**目标：** 在动手之前先理解代码。

1. **绝不猜测文件位置**：在尝试读取文件之前，先用搜索工具（如 `grep_search` 或目录列举工具）定位它们。
2. **完整读取所有目标文件**，使用 View 工具。不要略读。如果某个文件超过 500 行，只读取相关的函数/类——但要记下文件的边界。
3. **识别语言并确认基线**：在 `language-profiles.md` 中查找匹配的条目。在任何改动*之前*先运行一次测试命令，确保基线是绿的。如果未列出，请询问：*"你们用什么命令运行测试？"*——只问一个问题，然后继续。
4. **找到测试入口**：使用搜索工具或 glob 模式定位测试文件。
5. **只提一个澄清问题**，前提是范围确实存在歧义（例如："我是只重构这个函数，还是整个类？"）。不要提多个问题。如果范围清晰，跳过此步。

本阶段不要做任何编辑。

---

## 阶段 2：坏味道检测（Smell Detection）

**目标：** 先诊断，后开方。

1. 对照你刚读过的代码，逐一排查 `smells.md` 中的各个坏味道家族。**为节省 token**，不要完整加载 `smells.md`；用 `grep_search` 查找候选项，并且只查看目标行范围。
2. 对检测到的坏味道分级：
   - **阻断级（Blocker）**——妨碍理解或修改（例如 200 行的函数、上帝类）
   - **严重级（Major）**——明显的重复、耦合或复杂度
   - **轻微级（Minor）**——命名、细小的结构问题
3. 在采取任何行动之前，以带编号的列表呈现发现结果：

```
检测到的坏味道（已分级）：
1. [Blocker] 过长函数（Long Method）—— orders.ts:45 处的 processOrder()（142 行）。建议：Extract Method（提炼函数）。
2. [Major] 重复代码（Duplicate Code）—— 折扣逻辑在 orders.ts:67 和 cart.ts:23 重复出现。建议：Extract Function（提炼函数）。
3. [Minor] 基本类型偏执（Primitive Obsession）—— price 以裸 float 传递。建议：Replace with Money value object（用 Money 值对象替换）。
```

4. **此时不要改动任何代码。** 如果用户给出了一个具体的操作（而不是"把这段代码清理一下"），跳过坏味道检测，直接进入阶段 4。

---

## 阶段 3：制定计划（Planning）

**目标：** 在动手之前，就先做什么、按什么顺序做达成一致。

1. 把商定的工作拆解成**原子步骤**——每一步就是一次重构操作。
2. 每一步都必须：
   - 可独立验证（仅完成这一步后，测试就能确认它）
   - 自身不破坏现有功能（不是某个操作的一半）
   - 范围限定为最小必要改动
3. 在开始前明确说明步骤顺序：

```
计划：
1. 从 processOrder()（第 67–89 行）中提炼 calculateDiscount()
2. 从 processOrder()（第 91–110 行）中提炼 applyTaxes()
3. 内联 processOrder() 剩余的函数体 —— 现在只有 15 行
```

4. **标出任何涉及公共 API、序列化或并发的步骤。** 在把它纳入计划之前，请求用户明确确认。
5. 检查 `safety.md` §3 红线（为节省 token，只查看 `safety.md` 的第 41–101 行）。如果命中任何一条，停下来先解决它再继续。

---

## 阶段 4：执行循环（Execution Loop）

**对计划中的每一步重复此循环：**

### 每次编辑之前 —— 原子步骤检查清单
在写下任何一个字符之前，逐项确认：
- [ ] 范围已定义（确切是哪个函数/类/哪些行）
- [ ] 测试存在且当前通过（如果近期没有验证过，现在就运行）
- [ ] 本次改动保持公共 API 与外部行为不变
- [ ] 这恰好是一处逻辑改动——没有夹带任何其他内容
- [ ] 产生的 diff 能在 2 分钟内完成评审

### 每次编辑期间
1. **说明操作**：*"正在执行：Extract Method —— 将第 67–89 行提炼为 `calculateDiscount()`"*
2. **用代码块展示 before/after**：
```
BEFORE:
  // 第 67-89 行内联在 processOrder() 中
  let discount = 0;
  if (user.isPremium) { discount = price * 0.2; }
  ...

AFTER:
  function calculateDiscount(user, price) { ... }
  // processOrder() 现在调用 calculateDiscount(user, price)
```
3. **应用改动**，使用你的编辑/替换工具。
4. **语法/Linter 检查**：如果代码库是强类型的或配有 linter，在运行测试套件之前先运行一次快速的静态检查（例如 `tsc --noEmit`、`eslint`、`mypy`、`cargo check`），确认没有引入明显的编译期错误。
5. **运行测试**，使用终端工具。展示确切的命令和输出。
5. **测试失败时：**
   - 立即回退该编辑（用 Edit 恢复原始内容）
   - 说明：*"正在回退：[操作名] —— [测试名] 失败，错误为：[确切错误]"*
   - 诊断根因。提出更安全的拆解方式。
   - 不要试图"向前修"。不要进入下一步。
6. **测试通过时：** 确认：*"步骤 1 完成。测试通过。"* 然后进入下一步。

### 特殊情况
- **没有测试套件：** 在开始之前说明：*"未找到测试。在用户明确知悉行为验证需人工进行的前提下继续。"* 并要求用户确认。
- **测试耗时超过 30 秒：** 找出一个子集（例如 `pytest tests/orders/`）并运行它。说明跳过了哪些测试。
- **编译型语言：** 除测试之外，还要运行构建/类型检查（`tsc --noEmit`、`go build ./...`、`cargo check`）。

---

## 阶段 5：收尾（Wrap-Up）

**目标：** 让用户完整了解改了什么、接下来做什么。

1. **汇总表：**

```
已应用的改动：
┌─────────────────────────────────────┬──────────────┬──────────────┐
│ 操作                                │ 文件         │ 行数增减     │
├─────────────────────────────────────┼──────────────┼──────────────┤
│ 提炼函数 → calculateDiscount         │ orders.ts    │ +12 / -14    │
│ 提炼函数 → applyTaxes                │ orders.ts    │ +10 / -11    │
└─────────────────────────────────────┴──────────────┴──────────────┘
净效果：processOrder() 从 142 行减少到 38 行。
```

2. **范围纪律说明：** *"我没有动：cart.ts、user.ts —— 那里的重复折扣逻辑是另一个坏味道（检测结果中的第 2 项）。建议在后续工作中处理。"*

3. **后续建议**（仅列出——未经用户要求不要动手实施）：
   - 阶段 2 中检测到但尚未处理的其余坏味道
   - 本次重构新引入或新暴露的坏味道
   - 相邻文件中的相关改进

## 长期项目协议（Multi-Session Protocol）

**触发条件（任一成立即适用）：**

- 重构范围超过 100 个文件
- 范围是整个项目的语义重架构（术语归一 + 架构重划）
- 需要多个上下文窗口才能读完的审计工作
- 用户表述为"全项目"、"整个项目"、"重做底层"

一次会话承载不了这类范围。**不要试图在一次会话里硬做完**——上下文会溢出，结论会开始自相矛盾。下面的纪律跨会话生效。

### 1. 切片，一次会话只推进一个

把项目切成可审计的单元。优先按**数据聚合**切（围绕同一批表/字段的代码天然属于同一概念族），其次按部署/运行单元切，最后才按目录切——迭代生成的项目里，目录结构常是事后归类的产物，不足以作为切片依据。目标每片 5–20 个源文件，能在一次会话内读完并得出结论。

切片内做完、验证完、落盘完，再结束会话。切片清单落盘到 `REFACTOR-PROGRESS.md`：切片名、文件清单、状态（未开始 / 进行中 / 已完成 / 阻塞）、产出文件、遗留问题。

### 2. 状态必须落盘

跨会话恢复**只靠文件**，不靠聊天记录。维护两个状态文件：

| 文件 | 内容 | 更新时机 |
|---|---|---|
| `REFACTOR-STATE.md` | 当前批次、已完成批次、下一步的具体入口、阻塞项 | 每次会话结束 |
| `REFACTOR-PROGRESS.md` | 切片清单与各切片状态、产出文件、遗留问题 | 每完成一个切片 |

### 3. 会话开始：先读状态，再跑基线

1. **先读 `REFACTOR-STATE.md` 与 `REFACTOR-PROGRESS.md`。** 不要凭记忆或猜测继续。
2. **确认工作区干净**：`git status`。若有未提交改动，先弄清楚它属于哪个批次，再决定继续还是回退。
3. **跑一次行为基线**，确认基线仍然全绿（`python -m pytest`、`npm test` 或 `language-profiles.md` 中对应语言的命令）。上一个会话的结论可能建立在已经失效的代码上。
4. **复述本次要做的批次与下一步入口。** 若状态文件与代码现状矛盾，**以代码为准**，并立即修正状态文件。

### 4. 会话结束：更新状态，留下具体入口

```
REFACTOR-STATE.md（会话结束时的追加）：
- 完成：批次 3「订阅与计费」的命名归一；orders.ts 与 billing.ts 共 14 处改名
- 未完成：billing.ts 的重复折扣逻辑（检测结果第 2 项），已判定为下一批
- 下一步入口：读 billing/ 下 4 个文件，确认「计费主体」与「账户」是否同一概念；
  依据是 billing_subject 表与 accounts 表是否在同一事务内被一起修改
- 基线状态：全绿（未运行：无；新增失败：无）
- 阻塞：无
```

**「下一步：继续重构」是不合格的写法**——下个会话的你无法从中恢复。要写清楚：读哪些文件、回答哪个具体问题、按什么依据判定。

### 5. 跨会话的纪律

- **一个批次 = 一个可独立验证、可独立回滚的变更集。** 不把一个批次拆散到多次会话，也不在一个批次里夹带第二个批次。
- **批次中断必须记录失败原因**，包括"不要再试的方向"。测试失败、范围判断错误、契约未收敛——写进 `REFACTOR-STATE.md`，含确切错误信息与已回滚到哪个 commit。**不要留下"改了一半"的工作区。**
- **长会话中文件可能已被改动**：编辑前重新读取（见下方「快速规则」）。

### 6. 与其他规则的关系

- 单点坏味道（一个长函数、一处重复）**不适用本协议**，照阶段 1–5 的普通流程走。
- 改名与删除的前置条件、红线与契约处置规则见 `safety.md` §9。
- 语义漂移类坏味道的清单与取证方式见 `smells.md` 家族 7。

---

## 快速规则（始终生效）

- 绝不读完文件就立刻编辑它——永远先说明计划
- 绝不在一次 Edit 调用中夹带两处逻辑改动
- 绝不在重构过程中添加新行为（不要"顺手"修 bug）
- 绝不因为"只是个重命名"就跳过测试——重命名会破坏调用方
- 在长会话中，绝不假设文件自你上次读取后没有变化——编辑前重新读取
