# 阶段 0：行为冻结（Behavior Freeze）

> [!IMPORTANT]
> 本阶段是整个重架构的**硬性前置**。没有可复现的行为基线，任何「功能没变」的断言都是猜测。
> 在没有基线的情况下修改业务代码，属于红线，必须停下来先补基线。

## 为什么这一步不可跳过

AI 迭代生成的项目有个普遍特征：**没有测试，或测试是「跟着实现写的」**（实现改了，测试跟着改，
所以测试永远绿，但它不能证明任何东西）。

重架构会大规模改动命名与结构。此时唯一能证明「功能没变」的东西，就是**在改动之前录下来的行为**。
行为冻结就是把「当前系统的实际行为」变成一份**可重复执行的证据**，而不是一段回忆。

本阶段**只观测，不修改业务代码**。允许新增测试文件与测试基础设施。

---

## §0.1 可观测契约的四层

不要泛泛地说「行为」。行为必须被枚举成**具体契约点**。按下列四层逐层清点：

| 层 | 契约点 | 采集方式 | 破坏后果 | 典型判定 |
|---|---|---|---|---|
| **L1 对外交互面** | HTTP 路由+方法+状态码+响应体字段、GraphQL schema、CLI 参数与 stdout、SDK 公共方法签名、Webhook payload、页面路由 | 路由表/装饰器/`grep` 路由注册；实际发请求录制响应 | 下游调用方立即报错 | 高敏感，默认保留 |
| **L2 数据契约** | DB 表名/列名/类型/约束/索引、迁移历史、缓存 key 与结构、ES 索引、消息队列 topic 与消息体、文件格式 | schema 文件、迁移文件、实际 `DESCRIBE`、序列化器定义 | **数据损坏，最难回滚** | 最高敏感 |
| **L3 集成契约** | 第三方 API 调用形态、回调协议、鉴权 token 格式、签名算法 | 客户端封装处、出站请求日志 | 与外部系统断连 | 高敏感 |
| **L4 可观测行为** | 日志格式与级别、错误码与错误信息文案、指标名、告警规则、健康检查路径 | `grep` 日志调用与错误构造；指标注册处 | 监控失明、告警失效、运维脚本挂掉 | 中敏感，易被忽略 |

> [!WARNING]
> **L4 最常被漏掉，也最容易在重架构中悄悄破坏。**
> 换个错误信息文案、改个日志字段名，就足以让运维的告警规则和解析脚本失效。
> 清点 L4 的成本很低（grep 就够了），不要省。

**清点顺序**：L2 → L1 → L3 → L4。先数据后交互，因为数据契约最难回滚，
早发现早决策。

### 每条契约点的处置标注

清点时同步判定，三选一，**不允许留空**：

- `KEEP` —— 必须保持不变。重架构中最强的约束。
- `BREAK-PLANNED` —— 计划破坏。必须走 [migration.md](migration.md) 的四件套。
- `UNKNOWN` —— 还不确定，**必须在阶段 2 结束前收敛为 KEEP 或 BREAK-PLANNED**。

`UNKNOWN` 计数是阶段 0 → 阶段 2 的进度指标。带着 `UNKNOWN` 进入阶段 3 是红线。

## §0.2 清点方法（语言无关）

### L2 数据契约优先

```
# 找迁移文件（最权威的表结构演进记录）
glob: **/migrations/**, **/migrate/**, **/*.sql, **/alembic/**, **/prisma/schema.prisma
# ORM 模型定义
grep: class .*\(.*Model\)|@Entity|@Table|Schema\(|define\(|sequelize.define
# 缓存与队列
grep: redis|memcached|kafka|rabbit|sqs|pubsub|bull|celery
```

对每张表/每个索引记录：名称、列名与类型、约束、被哪些代码读写（这组信息在阶段 1
会直接成为概念映射的骨架）。

### L1 对外交互面

```
# 路由注册
grep: @app\.(get|post|put|delete)|router\.(get|post)|@RequestMapping|@GetMapping|HandleFunc|\.route\(|path\(
# 请求/响应模型（字段名的真值来源）
grep: class .*Request|class .*Response|class .*DTO|Schema|serializer|zod|pydantic
```

对每个端点记录：方法、路径、入参字段、出参字段、状态码、错误码。
**字段名是数据契约的一部分**——改字段名等于破坏契约。

### L3 集成契约

```
grep: http\.(get|post)\(|requests\.(get|post)|axios|fetch\(|httpx|RestTemplate|WebClient
grep: signature|hmac|jwt|oauth|Bearer|api[_-]?key
```

### L4 可观测行为

```
grep: logger\.|log\.(info|warn|error)|print\(|console\.log|logging\.
grep: raise .*Error|throw new .*Error|errors\.New|Exception\(
grep: prometheus|counter|histogram|gauge|statsd|datadog|otel
```

## §0.3 无测试／低覆盖项目的基线建立

这是 AI 生成项目的**常态**，也是本技能最核心的实操内容。目标不是「补出一个完整测试套件」，
而是**用最小成本钉住最关键的契约**。

### 步骤 1：先探测，别先写

```bash
# 找出项目自己认为的测试入口
cat package.json | grep -A5 scripts     # Node
ls pytest.ini tox.ini setup.cfg pyproject.toml   # Python
ls *_test.go                             # Go
ls pom.xml build.gradle.kts              # Java/Kotlin
```

**先跑一次现有测试，记录真实结果。** 三种情况分别处理：

| 情况 | 处理 |
|---|---|
| 有测试且全绿 | 直接作为基线。记录命令与耗时。 |
| 有测试但有失败 | **不要修**。把失败用例逐条列进 `BEHAVIOR-CONTRACT.md` 的 `KNOWN-FAILING` 段，标注失败原因。基线 = 「这些失败是已知的」。 |
| 测试不稳定（flaky） | 不要用重试掩盖。定位非确定性来源（时间、随机、并发、网络），在测试中固定它。若无法固定，标记为 `NON-DETERMINISTIC`，该路径的契约改用**黄金样本比对**覆盖。 |

### 步骤 2：按 ROI 排序，抽特征化测试

**特征化测试（characterization test）的目的不是断言「正确的行为」，而是断言「当前的行为」。**
哪怕当前行为是错的，也要先钉住——因为「保持不变」是重架构的契约，修 bug 是另一件事。

按下列 ROI 顺序补，做到「够用」就停：

1. **L2 数据读写路径** —— 用真实或容器化的 DB，跑一遍核心写路径，断言落库结果。
2. **L1 关键端点的完整往返** —— 发请求，断言状态码与响应体**结构**（字段名集合），
   值可以是宽松匹配。
3. **核心领域逻辑的纯函数** —— 这类最容易测、最稳定，性价比最高。
4. **错误路径** —— 至少覆盖会被外部依赖的那几个错误码。

不要去追求覆盖率数字。**覆盖率不是本阶段的目标，契约覆盖才是。**
判断标准：阶段 1 识别出的每一个「核心概念」，都至少有一条基线能证明它当前的行为。

### 步骤 3：录制式基线（当写测试成本过高时）

对庞大的遗留项目，比手写测试更快的方式是**录真实流量**：

- HTTP：把真实（或构造的）请求/响应对录成快照文件，改动后重放比对。
- 领域逻辑：给定固定输入集，把当前输出（含序列化结果）落成黄金样本文件。
- 数据层：把当前 DB 的 schema dump + 关键表的样本数据落成文件，改动后 diff schema。

**黄金样本的关键纪律**：样本文件必须提交进仓库，且**在重架构期间不允许因为「输出变了」
而更新样本**。样本变了，只有两种合法解释：① 你承认功能变了（那是 bug），
② 这条契约在 `BEHAVIOR-CONTRACT.md` 里被标为 `BREAK-PLANNED`。

### 步骤 4：为非确定性因素做接缝

重架构会移动代码，隐藏的全局依赖会暴露出来。提前把不可控因素收敛到接缝后面：

| 因素 | 做法 |
|---|---|
| 当前时间 | 注入 clock，不用 `now()` 直取 |
| 随机数/UUID | 注入 generator，或在测试中固定种子 |
| 网络/第三方 | 接缝 + 录制回放（stub 掉出站调用） |
| 并发/顺序 | 测试中固定并发度；依赖顺序的地方显式排序 |
| 环境变量/配置 | 测试启动时显式设置全部必需项 |

接缝注入本身是**结构性改动**。如果必须改业务代码才能建立接缝，先把该改动作为
**独立的最小批次**执行（只加接缝，不改逻辑），并单独验证。

## §0.4 交付物：`BEHAVIOR-CONTRACT.md`

必须落盘成仓库里的版本化文件。模板见 [templates/BEHAVIOR-CONTRACT-template.md](../templates/BEHAVIOR-CONTRACT-template.md)。

最低要求：

1. **基线运行方式** —— 一条命令（或明确的命令序列）能复现基线，记录耗时。
2. **基线状态** —— 通过 / 已知失败清单 / 非确定性标记。
3. **契约点表** —— 四层逐条列出，每条含：位置、当前行为、处置（KEEP / BREAK-PLANNED / UNKNOWN）。
4. **护栏** —— 哪些路径**没有**基线覆盖。这份清单决定了后续允许改动的范围边界。
5. **环境前提** —— 依赖的 DB、服务、环境变量、容器。

### 基线可信度自检

在进入阶段 1 之前逐项确认。**任一项为否则不得进入阶段 1**：

- [ ] 一条命令可复现基线，且我亲手跑通过
- [ ] 基线结果已记录（含失败清单），不依赖记忆
- [ ] 每个核心业务路径至少有一条基线覆盖（见 §0.3 步骤 2 的判定标准）
- [ ] 所有非确定性因素已被固定，或已明确标记为 `NON-DETERMINISTIC` 并改用样本比对
- [ ] L2 数据契约已完整清点（表、列、类型、索引）
- [ ] L1 契约点已完整清点，字段名已记录
- [ ] `UNKNOWN` 项已列出（允许存在，但必须有清单）
- [ ] 契约文件已提交进 git

## §0.5 基线的运行纪律

重架构期间，基线是**门禁**，不是参考。

1. **每个批次结束必须跑基线。** 只跑改动相关子集也可以，但批次收尾必须跑全量。
2. **基线失败即回滚该批次**，不要往前修（沿用 `references/process.md`
   的执行循环纪律）。
3. **基线本身不允许在重架构期间被「顺手更新」**。如果基线失败是因为你改了行为，
   停下来判定：是 bug（回滚）还是计划内的契约破坏（走迁移流程）。
4. **基线变绿不算完**，还要确认它**没有变成空跑**。一个常见陷阱是重构后测试不再覆盖原路径
   （例如 mock 掉的东西变多了），此时测试依旧绿但已失效。
   每个批次收尾检查一次：新增/修改的代码是否仍在基线覆盖范围内。
5. **基线耗时超过 5 分钟时**，建立分层运行方案：批次内只跑相关子集，批次收尾跑全量，
   并明确记录跳过了什么。

### §0.5.1 删除类改动为什么需要额外验证

**删除不是行为保持，而是行为缩减。** 命名归一与结构改动要求「基线结果完全一致」，
而删除会让某些路径彻底消失——基线的通过并不能证明删对了，只能证明
**被基线覆盖的路径没被误删**。

因此删除批次在此之上还有三项额外要求：

1. **必须有独立的取证记录**，而不是「基线绿所以能删」。
   取证协议见 [dead-code-removal.md](dead-code-removal.md)。
2. **必须有覆盖边界说明**：基线覆盖不到的路径，删除结论的证据强度要如实标注。
3. **必须登记观察项**：删除后基线绿只是通过第一道关。
   路线 A 需覆盖一个完整业务周期；路线 B 需由用户实际走查主要流程，
   并把观察项写进 `REARCH-STATE.md` 留待下一轮验证。

> [!WARNING]
> 「基线绿了所以删对了」是删除类改动最常见的误判。
> 基线只覆盖它覆盖的东西；没被覆盖的低频路径被删掉了，基线依然全绿。

## §0.6 收尾输出

阶段 0 完成的标志是这三句话都能成立：

1. 「我可以用一条命令复现当前系统的行为基线。」
2. 「我知道哪些行为是被钉死的（KEEP）、哪些准备改（BREAK-PLANNED）、哪些还不确定（UNKNOWN）。」
3. 「我知道哪些路径没有基线覆盖，因此哪些区域在本次重架构中不能动。」

先读 [session-state.md](session-state.md) 规划切片。
