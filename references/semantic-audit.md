# 阶段 1：语义审计与逆向建模（Semantic Audit）

> **本阶段禁止修改业务代码。** 只读代码，只写文档。
> 「审计着审计着顺手改了一下」是本阶段最常见的失控方式。

## 阶段目标

回答三个问题，并把答案落盘：

1. **这个项目里到底有哪些概念？**（术语表）
2. **每个概念分别落在哪些代码上？**（语义地图）
3. **哪些地方的名字和实际语义对不上？**（漂移清单）

产出三件套：`GLOSSARY.md`、`SEMANTIC-MAP.md`、`DRIFT-REPORT.md`。

---

## §1.0 第一条纪律：取证，不要推断

AI 生成项目的命名**不可信**。一个叫 `UserManager` 的类可能实际在做鉴权、
也可能是订单的附属逻辑、也可能已经废弃。

因此每条审计结论必须有**证据**，证据只有四类，其余都算猜测：

| 证据类型 | 说明 | 强度 |
|---|---|---|
| **数据形状** | DB 表/列、序列化字段、API 出入参 —— 它们描述概念的真实结构 | 最强 |
| **调用关系** | 谁调用它、它被谁依赖 —— 决定它属于哪个概念边界 | 强 |
| **行为断言** | 测试断言、校验逻辑、错误分支 —— 说明它承担的不变量 | 强 |
| **命名本身** | 标识符文字 —— 只能作为**线索**，不能作为结论 | 最弱 |

> [!WARNING]
> 只凭命名下结论，会产出「看起来很专业但全错」的术语表。
> 典型错误：把 `AccountService` 拆成「账户」概念，而实际上它一半在管订阅、一半在管权限。
> **必须看它读写哪些字段、被谁调用。**

## §1.1 切片：把项目切成可审计的单元

>100 文件的项目**不可以**一次性审计。上下文预算会爆，结论会开始互相矛盾。

切片原则，按优先级：

1. **优先按数据聚合切** —— 一组围绕同一批表/字段的代码天然属于同一概念族。
   这是最可靠的切片依据，因为它绑定在真实数据上。
2. **其次按部署/运行单元切** —— 服务、进程、CLI 子命令、前端路由区块。
3. **再次按目录切** —— 最省事但最不可靠，因为 AI 生成项目的目录结构常常是
   事后归类的产物，与真实语义边界不一致。
4. **切片大小目标**：每个切片 5–20 个源文件，能在一次会话内读完并产出结论。
   太大就再切，太小就合并。

每个切片记录在 `AUDIT-PROGRESS.md`：切片名、文件清单、状态、产出文件、遗留问题。
**一次会话只处理一个切片。** 跨会话恢复方式见 [session-state.md](session-state.md)。

## §1.2 概念提取：从代码里捞出候选概念

### 手工路径（切片较小时首选）

**步骤 1：列出全部标识符，按词根聚簇**

重点看这些位置：类型/类名、模块与文件名、DB 表与列名、API 路径与字段名、
枚举与常量、领域层的方法名。

```
# 类型与类
grep: ^\s*(export )?(class|interface|type|enum|struct|record) \w+
# 表与列（迁移文件最全）
grep: CREATE TABLE|add_column|column\(|@Column
# API 路径与字段
grep: (get|post|put|delete)\(|path\(|@Path|@GetMapping
```

把结果按**词根**聚簇。例如出现 `order` 的：`OrderController`、`order_items`、
`/api/orders`、`OrderDTO`、`orderStatus`。这些是**同一个概念**的多个投影。

**步骤 2：为每个聚簇找「真值来源」**

同一概念在多个地方出现时，哪一个是权威？判定顺序（详见 §1.5）：

```
数据形状 > 数据库 schema > 对外 API > 领域层类型 > 其他
```

**步骤 3：读实现，写一句话定义**

对每个候选概念，必须能写出这样一句话：

> X 是一个 **<概念类型>**，表示 **<什么>**，它的关键不变量是 **<约束>**，
> 权威定义在 **<文件:行>**。

写不出来 → 该概念还没被理解，继续读实现，或标记为 `UNRESOLVED`。
**`UNRESOLVED` 是合法结论**，比编一个定义强得多。

**步骤 4：建立证据链**

每个概念在 `SEMANTIC-MAP.md` 中必须列出证据来源（表名、类名、路由、断言位置）。
没有证据的概念不进术语表。

### 自动化路径（项目很大时）

LLM 辅助审计可以大幅提速，但**必须约束输出格式**并要求证据。可用提示词骨架：

```
阅读以下文件：<文件清单>

任务：为这个代码切片产出概念清单。严格遵守：
1. 只报告有证据支撑的概念，证据必须是「表名/字段名/调用关系/断言」之一，
   不得以命名本身作为唯一依据。
2. 每个概念给出：建议中文名、建议英文标识符、一句话定义、关键不变量、
   证据（文件:行 + 证据类型）。
3. 明确列出：同名不同义、同义不同名、无法判定的项（标 UNRESOLVED）。
4. 不要提出改进建议，不要重构，只做描述。
5. 输出为 Markdown 表格。
```

> [!CAUTION]
> 自动化的产物是**候选清单，不是结论**。凡是要写进 `GLOSSARY.md` 的条目，
> 必须由你亲自打开对应文件核对证据。AI 很容易把「名字相似」当成「概念相同」——
> 这正是我们要修的那个毛病，不要让审计工具自己犯。

## §1.3 漂移分类（本阶段的核心产出）

把候选概念与代码现状对照，逐条归类。五种漂移，各有不同的处置方式：

### D1 同名不同义（One Name, Many Meanings）——**最危险**

同一个名字在代码里指两件不同的事。例如 `status` 在订单上下文表示支付状态，
在物流上下文表示配送状态；`Account` 在一处是登录账号，在另一处是计费主体。

- **危害**：任何一处按名字做的改动都会误伤另一处；新加入的人必然误解。
- **证据**：同名标识符出现在**不同的数据表/字段**上，或赋值来源互不相干。
- **处置**：拆成两个概念，其中一个改名。属于**命名归一**（阶段 2）。
- **优先级**：Blocker。它会持续制造误改。

### D2 同义不同名（Many Names, One Meaning）——**最普遍**

同一件事有多个名字：`user` / `account` / `customer` / `member` / `client` 混用；
`getX` / `fetchX` / `loadX` / `queryX` 混用；`cart` / `basket` / `tray` 混用。

- **危害**：认知负担，搜索不全，改动漏改（这类项目「改了 A 忘了 B」的根源）。
- **证据**：不同名字指向同一张表/同一批字段，或可互相赋值。
- **处置**：选一个主名（依据 §1.5 真值来源），其余列为别名，统一改名。
- **优先级**：Major。分批处理，按影响面从小到大。

### D3 名实不符（Misleading Name）

名字说 A，实际做 B。例如 `validate()` 里在写数据库；`isValid` 其实是
「是否已支付」；`Utils` 里装着核心业务规则；`temp` 是长期存在的关键逻辑。

- **危害**：误导阅读者，是理解成本的主要来源。
- **证据**：实现里出现与名字语义无关的副作用（IO、状态变更），
  或名字描述的条件与实际判断条件不一致。
- **处置**：拆解——把副作用抽出来（结构改动），再把剩下的改名。
  **注意这是两类改动，必须分成两个批次**，先结构后命名。
- **优先级**：Major。

### D4 幽灵概念（Ghost Concept）

代码里有完整实现，但业务上根本不存在这个概念。AI 迭代的典型产物：
早期方案残留、被替换但没删的旧路径、为假想需求做的抽象、废弃的 feature flag 分支。

- **危害**：占用认知与维护成本，混淆真值来源，让审计得出错误结论。
- **证据**：无调用点（含动态调用、反射、路由注册、事件订阅、外部触发），
  且数据表里无数据或仅有历史数据。
- **处置**：确认无引用后删除。**删除是最难回滚的操作之一**，必须：
  ① 全量搜索引用（含字符串形式的动态引用、配置、文档、CI 脚本）；
  ② 确认表/字段是否仍有历史数据与合规保留要求；
  ③ 单独一个批次，不与任何其他改动混合。
- **优先级**：Major，但风险等级高。宁可先标记后处理。

### D5 缺失概念（Missing Concept）

业务上明确存在一个概念，但代码里它**没有名字**——散落在多个地方，
靠重复的字段组合或条件表达式隐式表达。典型例子：折扣计算规则散在 5 个文件里；
「会员等级」靠 `if (total > 1000 && days < 30)` 到处重复判断。

- **危害**：改一处漏一处；无法复用；没有地方承载不变量。
- **证据**：同一组字段/条件在 3 处以上重复出现，且语义一致。
- **处置**：引入概念（值对象 / 类型 / 模块），把散落的表达收敛进去。
  这是**结构改动 + 新增抽象**，按 `catalog-composing.md` 与
  `catalog-api.md` 的手法执行，风险高于纯改名。
- **优先级**：Major/Blocker，视重复范围而定。

## §1.4 漂移评分与优先级

每条漂移按下表打分，总分决定处理顺序。**先处理高分项**，因为它们的收益/风险比最高。

| 维度 | 3 分 | 2 分 | 1 分 |
|---|---|---|---|
| **波及范围** | >10 个文件 | 3–10 个文件 | 1–2 个文件 |
| **误改风险** | 已造成过 bug | 极易误改（同名不同义） | 只是难读 |
| **外部可见** | 出现在对外 API/DB | 出现在日志/错误码 | 纯内部 |
| **契约状态** | 全部 KEEP（改名即破坏） | 部分 BREAK-PLANNED | 全部 BREAK-PLANNED |

- **总分 ≥ 8**：Blocker，优先做，但先确认契约处置
- **总分 5–7**：Major，排进批次
- **总分 ≤ 4**：Minor，最后处理或列入后续

> [!NOTE]
> **契约状态得低分不代表简单，而代表危险。** 一个高分且契约全是 `KEEP` 的项，
> 意味着它很重要又不能破坏——这类项必须先设计迁移方案（[migration.md](migration.md)）
> 再动手。

## §1.5 真值来源判定协议

当同一个概念在多处有不同表述时，必须判定哪一个是权威。**判定顺序是固定的**，
不允许因为「代码里这个用得最多」就选它：

1. **数据形状** —— 数据库实际存储的列与类型。数据最难改，也最真实。
2. **数据库 schema / 迁移文件** —— 表结构演进的历史记录。
3. **对外 API 契约** —— 已经承诺给下游的字段名。
4. **领域层类型定义** —— 内部模型的正式声明。
5. **使用频率最高的名字** —— 只有在以上都缺失或矛盾时才用这条。

**冲突处理**：如果第 1 层与第 3 层矛盾（DB 用 `cust_id`，API 用 `customerId`），
**两者都保留**——它们属于不同层的契约。真值来源只用来决定**内部代码**统一用哪个名字，
以及**新代码**该叫什么。

> 这条区分很重要：内部命名归一 ≠ 对外契约改名。
> 把两者混为一谈，是重架构项目炸掉的头号原因。

## §1.6 跨切片归纳

所有切片审计完后，做一次全局归纳。这一步经常暴露切片内部看不出的问题：

1. **合并重复概念** —— 不同切片各自识别出的概念，可能是同一个。
   用 §1.5 的判定协议决定主名。
2. **识别跨切片概念** —— 贯穿多个切片的概念（例如「租户」「权限」）通常是核心域，
   应优先获得清晰的边界与命名。
3. **汇总漂移清单** —— 按 §1.4 评分排序，形成全局优先级。
4. **汇总 `UNRESOLVED` 项** —— 逐条给出处置：继续调研、问用户、或明确列入不处理范围。
   **不允许静默丢弃。**
5. **检查自相矛盾** —— 不同切片的结论是否冲突？冲突说明某个切片的证据不足，回去补证。

### 完成标准

阶段 1 完成的标志：

1. 每个切片都有审计记录，且记录了证据。
2. 每个核心概念都能写出「一句话定义 + 不变量 + 权威定义位置」。
3. 每条漂移都有分类（D1–D5）、证据、评分、契约处置。
4. `UNRESOLVED` 项已逐条处置，无静默丢弃。
5. 三个交付文件已提交进 git。

### 禁止事项

- ❌ 本阶段修改任何业务代码
- ❌ 以命名作为概念定义的唯一证据
- ❌ 用 AI 生成的概念清单直接充当结论而不核对
- ❌ 把 `UNRESOLVED` 当作「不重要」而丢弃
- ❌ 在契约处置未收敛为 KEEP / BREAK-PLANNED 之前进入阶段 2

下一步：读 [domain-extraction.md](domain-extraction.md) 确定目标模型与边界，
再读 [naming-normalization.md](naming-normalization.md) 把术语落到代码上。
